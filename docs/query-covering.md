# 查询字面量的多片段覆盖

本文汇总当前行为与验证入口。设计动机、完整执行流程、装饰器与大小写示例见[查询覆盖与分支执行优化设计](query-covering-optimization.md)。

2026-09-08 实现；最初覆盖实验的对照基线为 `7438754`。随后尝试了[固定字面量优先提取](../benches/results/fixed-literal-extraction-2026-09-08.md)和[统一限制组合数量](../benches/results/small-variant-extraction-2026-09-08.md)。当前改为保留分支内部覆盖，并按已知候选停止无效查表，见[本轮实验](../benches/results/branch-covering-2026-09-08.md)。字节对权重、gram 生成规则、索引格式版本 4 和刷新路径保持不变。

## 行为

原来每个字面量只选一个最长 gram。新方案保留这个键作为首选，再用互补的已索引片段约束字面量其余部分。当很多文件只共享原来的最长片段时，可以排除这些文件；所有候选仍需要完整正则验证。

`ngram::covering_hashes` 枚举现有规则允许的 gram，记录每个起点的最长片段。从左向右选择能延伸最远的片段，相邻片段至少重叠两字节，使完整覆盖包含字面量的每个 trigram 位置。选中片段按长度及起点降序排列，哈希去重，最多返回 128 个键。原来的最长 gram 始终排在第一位；长字面量超预算时得到部分覆盖，候选范围只会放宽。重复字节对应的相同键只保留一次。

查询规划的额外空间随字面量长度线性增长；索引构建仍采用原来的生成流程。覆盖不选择未建索引的两字节或超过 24 字节的 gram，也不要求重建旧索引。

## 分支与预算

第一遍的单字符类展开上限 `limit_class` 为 16，整体组合上限 `limit_total` 恢复为 128。只有整条查询没有任何完整可用字面量组，才以 128 / 128 重试。两个上限分别限制单个字符类和跨位置组合；16 不是整条查询的组合数或总 key 数。

例如 `["'](?:cuda|cpu|rocm)["']` 的 2 × 3 × 2 = 12 种带引号字面量会一起保留。多个小字符类的组合可以超过 16，仍受 128 的总上限约束。提取器超预算时可保留较短的必要片段，不能截断可选分支列表。

例如 `^[ \t]*@(?:torch|pytest)\.[A-Za-z_]+` 保留 `@torch.` / `@pytest.` 两个固定字面量，后缀字符类不再拼接成 106 个变体。在选 gram 前，还会去掉被其他字面量组包含的必要条件：只有较强组的每个分支都包含较弱组的某个字面量，才可删除整个较弱组。因此 `torch` / `pytest` 被更完整的装饰器字面量取代，但不能因为仅一个分支更长，就删除其他分支仍需要的条件。

固定字符串的每个覆盖键都是必要条件，直接求交。正则规划使用三层结构：组间求交、组内分支求并、分支内部的 gram 求交。字面量组提取与包含剔除沿用上一版；选键后还按实际 key 集合删除 OR 内被较宽分支包含的较严分支。

例如两个分支各要求 `A,B` 和 `C,D`，预算充足时执行完整的分支覆盖：

```text
分支一：postings(A) ∩ postings(B)
分支二：postings(C) ∩ postings(D)
该组候选：分支一 ∪ 分支二
```

执行先读取各组所有分支的首个 gram，建立完整初筛。再在当前候选内逐分支细化：优先处理新增 key 少的分支，同等情况下优先首个 posting 更短的分支；分支内先应用已缓存的 gram，按 posting 文件数升序处理。未知 gram 沿用原覆盖顺序。已被其他分支接纳的文件不再参与重复验证；剩余候选为空时停止该分支，整组已接纳所有当前候选时停止其余分支。

这保留了分支关系，避免仅含 A、D 的文件因跨分支混合而通过该组。它不记录文件内位置，仍需要最终正则验证；不对独立的必要字面量组做笛卡尔积。成本信息来自已经读取的 posting，不会为估算成本额外查询未知 key，也尚未使用解码前的 posting 长度预测。

只要任意变体不足三字节，整个提取条件就不可用。可选重复和单独的可选分支不被当成必要条件。128 个字面量变体、128 个条件组和 128 个实际查表键的限制继续生效。初筛预算不足时跳过整组；细化预算不足时放弃尚未读取的 AND 条件，但保留该分支已有候选。不能丢弃 OR 分支；没有完整初筛条件时全扫描。

## 验证

提取测试覆盖装饰器两分支、全部 12 种带引号设备名、小字符类的组合超过 16 时继续保留、必要片段保留、冗余组的全分支检查及展开回退。执行测试穷举四个 key 的全部 16 种出现组合，验证分支关系；另外检查安全提前停止及初筛、细化两阶段的预算回退。33 个单元测试、3 个 CLI 测试、1 个 Git 增量测试均已通过；clippy 和格式检查通过。各次 benchmark 的输出一致性及索引字节校验见对应版本报告。

- 随机字节、低熵字节和不同上下文验证每个覆盖键都存在于包含字面量的文档索引中，同时检查每个 trigram 位置的覆盖。
- 重复字节、短字面量、超过 128 个键的长字面量验证去重和预算。
- 长短不一的分支、可选分支、Unicode 大小写折叠和 512 种 ASCII 大小写组合验证不漏报。
- 实际 postings 执行测试验证共享最长 gram 的非匹配文件被新增片段过滤，以及预算耗尽后的匹配保留。
- CLI 集成测试把固定字符串、正则分支及忽略大小写的输出与全扫描正则结果比较。

性能实验复用 `benches/refresh_matrix.py`，在同一索引上随机交错运行基线与新版本，分别记录默认搜索和 `--no-refresh`。额外的 `benches/query_cover_metrics.py` 在临时副本中插桩，记录候选文件数、候选字节数、查表键数、解码后文档 ID 数量、查询规划时间和集合处理成本；插桩构建不用于完整 CLI 耗时比较。

`decoded_ids` 是 `DiskIndex::postings` 返回的有效文档 ID 数，单基础段语料中可直接用于比较列表解码规模；它不代表压缩字节读取量，也不计算多段查询中被版本过滤掉的旧 ID。`set_and_cache_ns` 包含集合运算、预算检查和查询缓存管理，不是纯集合操作微基准。

最初覆盖版本的[性能报告](../benches/results/query-covering-2026-09-08.md)记录了 110 项新旧输出一致、8 组语料索引段字节一致，以及全部候选/查表诊断。定向共享片段查询的默认延迟下降 41.3%，但原有矩阵没有显示普遍加速；候选不变而新增大量 postings 的查询存在回退。这些数字不能用来判断后续提取修正的收益。

中间版本“第一遍禁止字符类”的[报告](../benches/results/fixed-literal-extraction-2026-09-08.md)中，装饰器 key 数从 122 降到 3，候选保持 1,348 个，默认延迟下降 8.6%。原有 102 项查询整体基本持平。小字符类停止展开以及冗余字面量组被删除，都可能放宽实际 gram 过滤：110 项中 26 项候选增加，带引号设备名和张量创建查询出现明显回退。后续的 [16 / 16 实验](../benches/results/small-variant-extraction-2026-09-08.md)恢复引号过滤，但影响了大小写查询；当前结果见[分支覆盖报告](../benches/results/branch-covering-2026-09-08.md)。
