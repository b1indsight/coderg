# 从 2 GiB 到 518 MiB：coderg 建索引内存优化

coderg 在 vLLM 的 6,835 个文本文件、82.38 MiB 源码上构建索引，最终目录只有 66.40 MiB，原先的建索引峰值 RSS 中位数却达到 2,082.70 MiB。优化后，峰值降到 517.70 MiB，减少 75.1%；建索引耗时中位数从 2.478 秒降到 0.743 秒。生成的 lookup 和 postings 文件与原版逐字节一致。

这次优化围绕三个问题展开：同一组信息是否被重复保存，当前阶段是否还需要昂贵的数据结构，以及临时数据能否提前释放。

## 1. 先区分磁盘体积与构建工作集

磁盘索引已经使用压缩格式：单文档 posting 内联，多文档 ID 使用差分 varint，lookup 按 128 个键分块。66.40 MiB 的索引体积不能直接代表构建时的内存需求。

原来的数据流是：

```mermaid
flowchart LR
    A[并行读取文件] --> B[每文件 HashSet 去重 gram]
    B --> C[保留全部文件集合]
    C --> D[汇总 HashMap: gram → Vec 文件 ID]
    D --> E[键排序、列表排序和去重]
    E --> F[压缩编码写入索引]
```

文件集合回答“一个文件含有哪些 gram”，全局映射回答“一个 gram 出现在哪些文件”。构建过程中，这两种方向的表示同时存在，表达的却是同一组关联关系。

全局约有 798 万个不同的 gram 键。64 位平台上，`Vec` 通常包含指针、长度、容量三个机器字，元数据就占 24 字节；约 798 万份仅这部分就接近 183 MiB。还需要考虑键、哈希表空桶、各列表的堆内存、扩容余量，以及逐文件集合。

这个估算用于解释结构开销，并非逐分配的实测归因。RSS 还受到并行任务重叠和分配器保留页面的影响，不能把各数据结构的理论大小直接相加当作实测峰值。

## 2. 去重结束后，释放集合桶

生成 gram 时需要判断键是否已出现，`HashSet` 适合完成这一步。去重结束后，下游只需要遍历键，不再执行集合查询。

现在每个文件处理完成后立即将集合转为紧凑的 `Vec<u32>`，释放哈希表桶和空闲容量。每个保留下来的键占 4 字节。

汇总阶段再逐文件取走数组中的键，写入统一的记录区，并释放该文件的数组。`IndexedFile` 继续保留路径、文件 ID、长度和可搜索标记等元数据，用于构建 manifest。

关键是缩短两代中间表示同时存在的时间。即使两种结构分别都合理，让它们一直存活到函数结束，也会抬高峰值。

## 3. 用连续关联记录替代全局哈希表

新表示直接保存关联关系，每条记录是两个 `u32`，共 8 字节：

```text
(gram, 文件 ID)
(A, 3)
(B, 3)
(A, 8)
```

各文件去重后的键数量已经确定，因此可以预先求和，为所有记录一次分配足够的空间。汇总过程中不需要反复扩容。

按 `(gram, 文件 ID)` 排序后，记录变成：

```text
(A, 3)
(A, 8)
(B, 3)
```

同一个 gram 的记录连续，文档 ID 也已有序。编码器直接读取同键的连续切片，就能得到有序 posting 列表，无需再为每个键分配独立的 `Vec`，也无需复制一份键数组。

具体流程使用 Rayon 的并行原地不稳定排序，再统一去重。相同记录不需要保留输入顺序；排序后的键和 ID 顺序仍然确定。

设全部 gram—文件关联数为 P、不同 gram 键数为 U，新方案的排序一般为 O(P log P)，记录区占 8P 字节。它消除了全局哈希表和每键列表的结构开销，但内存仍随 P 增长。

### 为什么排序后反而更快

原版虽然使用哈希表汇总，后续仍要排序全部键及各键的文档列表。新方案的数据连续，减少了指针跳转和随机内存访问，同时省掉大量哈希表操作、小块分配与释放。

因此，渐进复杂度不能单独预测这里的实际性能。对当前语料，减少分配和改善内存访问带来的收益超过了统一排序的成本。其他文件数量、重复程度和文件大小分布仍需单独测量。

## 4. 按需获取字节对权重

稀疏 gram 的选择依赖相邻字节对的确定性权重。原实现先创建接近文件字节数长度的 `Vec<u64>`；一个 10 MiB 文件仅这个临时数组就需要约 80 MiB，并行处理时还可能叠加多个数组。

算法每次只检查当前最多 24 字节的扩展窗口。现在需要某个权重时才读取或计算：

- 输入达到 4,096 字节时，查询进程内共享的 65,536 项 `u64` 权重表，约 512 KiB，通过 `OnceLock` 延迟初始化。
- 小输入直接计算，短查询无需初始化整张表。

权重函数、gram 选择条件和最终哈希值保持一致。改变的是权重的获取和保存方式。此后无需为每个文件分配与文件长度成比例的权重数组。

## 5. 分阶段测量

环境为 Apple M5、10 个逻辑 CPU、24 GiB RAM，macOS arm64；Rust 1.94.0，release 构建。语料为 vLLM commit `569adb5a9780f9c02d22a6b29826acf711512356`。文件系统缓存为热缓存，各版本每次构建使用全新索引目录。

耗时测量为 1 次预热加 5 次计时；峰值 RSS 另测 3 次，不混入耗时统计。

| 阶段 | 峰值 RSS 中位数 | 建索引耗时中位数 | 索引目录 |
|---|---:|---:|---:|
| 原版 | 2,082.70 MiB | 2.478 秒 | 66.40 MiB |
| 紧凑数组、连续记录、直接编码 | 594.86 MiB | 0.754 秒 | 66.40 MiB |
| 再移除整文件权重数组 | 517.70 MiB | 0.743 秒 | 66.40 MiB |

主要收益来自中间表示的改造。移除权重数组又减少约 77 MiB；后两个阶段的耗时差较小，不能单独据此认定有稳定加速。

搜索也完整复测：28 个与 rg 输出一致的查询，每项预热 3 次、计时 31 次。默认搜索的查询中位数均值保持在 47.75 ms。另两项原有的跨行及空行计数语义差异继续排除出与 rg 的性能比较；全部 30 项输出与修改前一致。

## 6. 正确性和兼容性

编码器仍写版本 4 格式，单文档内联、差分 varint、128 键分块及偏移编码均保持一致。全量和增量 delta 构建共用新的汇总与写入路径。

验证包括：

- 18 个单元测试、2 个 CLI 集成测试、1 个 Git 增量集成测试通过。
- 编码往返覆盖无序记录、重复记录、跨块查找、`u32::MAX` 键与文档 ID，以及空段。
- gram 选择与独立的完整扫描参考实现比较，覆盖权重查表阈值两侧及长输入。
- 最终版 10 次构建的 lookup/postings SHA-256 与原版相同；归一化自动生成的段标识和文件名后，manifest 一致。
- 默认和 `--no-refresh` 两种模式下，30 类查询的完整输出、行数和退出码与原版一致。

旧索引可以直接使用，无需迁移。内存优化也适用于索引刷新时写入的新 delta 段。

提交优化后，又在 vLLM 临时克隆中模拟了未提交修改、提交已索引内容、直接提交 32 个文件的修改、同树空提交和缓存回退。32 文件提交后的首次默认搜索，峰值 RSS 中位数从 48.31 MiB 降到 27.98 MiB，耗时从 98.84 ms 降到 86.85 ms；提交推进、空提交和回退均未新增索引段。所有阶段的完整搜索输出和段内容一致。详见 [Git 状态转换 benchmark](../benches/results/vllm-git-transitions-2026-09-07.md)。

## 7. 适用边界

当前仍会完整读取每个文件，使用逐文件临时集合去重，并在内存中保存全语料关联记录。此次优化没有设置固定的内存上限，也没有引入磁盘外排。对于更大语料，工作集仍会增长。

新建索引的目录大小也不能代表长期使用后的磁盘体积。增量段和 Git 树缓存会随历史状态积累；`stats` 只报告当前引用的 manifest 和段。本次构建优化保持了这些现有行为。
