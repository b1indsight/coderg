# 决策：忽略大小写的索引查询暂用 128 / 128

- 状态：已接受并实施；用户确认「先用 128/128」。
- 决策日期：2026-09-07；相关实验进行于 2026-09-06 至 2026-09-07。
- 适用范围：coderg 使用现有索引规划、过滤正则搜索候选文件的预算。
- 当前配置：`MAX_LITERAL_VARIANTS = 128`，`MAX_INDEX_LOOKUPS = 128`。
- 实现位置：[query.rs](../../src/query.rs)、[search.rs](../../src/search.rs)。
- 证据入口：[实验报告](https://github.com/b1indsight/coderg/blob/5ca67a2470ac9e9e3b7cc08ad3f2b8115f68a170/benches/results/vllm-case-budget-2026-09-07.md)、[归档清单](https://github.com/b1indsight/coderg/blob/5ca67a2470ac9e9e3b7cc08ad3f2b8115f68a170/benches/results/data/vllm-case-budget-2026-09-07/manifest.json)。

本次选择是在当前 vLLM 工作负载下保留一个表现较好的默认值。实验没有证明
128 / 128 是所有仓库、所有查询的唯一最优点；64 / 128 也很接近。
与 128 / 256 的直接补测相比，128 / 128 的查询中位数均值快约 0.6%–0.7%，
p95 没有可确认的稳定差异。内存差距小，属于次要考虑。

## 1. 问题从哪里来

最初需求是在真实 vLLM 仓库上比较 coderg 与 `rg`，了解搜索耗时、内存占用、
索引文件大小，并继续检查正则搜索在什么情况下明显慢于 `rg`。

前期发现过 `.` 等高命中密度查询的慢例。用户指出这些不是主要日常场景，
因此后续用类型引用、函数定义、日志调用、平台名、配置项、异常类型等普通
代码搜索来选择参数。高密度匹配、输出收集和文件列表模式的提前结束问题，
没有作为本次预算调整的优化目标。

更值得解决的问题是 `-i`：它表示忽略大小写，使用正则引擎的 Unicode
大小写匹配语义。早期实现对这类查询没有可用的索引筛选，因而扫描全部
已索引文本文件。仅把查询转成小写无法直接复用原始大小写字节的索引。

讨论随后形成了两步工作：

1. 从正则中提取完整的大小写、分支变体，复用现有索引，缩小候选文件集合。
2. 给变体展开和索引读取设置预算，再用实验决定合适的默认值。

最初采用的 64 个变体 / 256 个索引键是工程上的起始预算，没有经过参数扫描，
也不是由概率模型或内存定理推导出的最优值。用户因此要求实验确定。

## 2. 128 / 128 分别限制什么

配置按「单片段变体上限 / 整条查询索引键上限」书写。

| 参数 | 当前值 | 含义 |
|---|---:|---|
| `MAX_LITERAL_VARIANTS` | 128 | 每次字面量提取的变体展开预算；同时传给提取器的 `limit_class` 和 `limit_total` |
| `MAX_INDEX_LOOKUPS` | 128 | 整条查询实际读取的不同索引键上限；重复键复用缓存，不重复计数 |

所以 128 / 256 表示最多 128 个片段变体、最多 256 个不同索引键。一个变体
会选取可用 gram 的哈希键；多个变体可能得到相同键，多个片段也可以共享键。
变体数、键数、底层磁盘访问次数、候选文件数和匹配结果数不是同一个计量。

**实现中存在一个耦合：**`MAX_INDEX_LOOKUPS` 还限制生成的筛选条件组数。
本次实验按现有代码同时改变这两个用途，没有把“条件组数预算”和“读键预算”
拆成独立参数。因此不能把所有变化都归因于读取键数这一项。

总变体需求和理论查键需求都可能超过预算，但实际接纳的完整过滤条件受预算约束。
查键前会检查 `cache.len() + new_hashes.len()`，超过上限就跳过整组条件。
这个上限是硬限制，不会先读到第 129 个键再停止。

当前没有基于“候选文件超过总数的某个百分比”来动态选择全量扫描的阈值。
这里的阈值是提取、规划和查键预算。

## 3. 使用现有索引的方法与正确性约束

索引保留原始字节的大小写：包含三字节 gram，以及较长的稀疏 gram。
查询从正则 HIR 提取必要的前缀、后缀，也检查拼接表达式中的连续三个 HIR
节点窗口，以避免为整个长标识符展开所有大小写组合。

提取结果按以下关系使用：

```text
某个必要片段的候选文件 = 该片段所有替代键对应文件集合的并集
整条查询的候选文件   = 多个必要片段候选集合的交集
最终结果             = 正则引擎在候选文件上验证出的真实匹配
```

必须保持以下约束：

- 同一条件的替代列表必须完整。不能保留前 128 个大小写或分支变体、丢弃剩余
  部分后仍把这组列表当成安全过滤条件。
- 提取器在展开预算不足时可以安全缩短字面量；无法得到完整、可用的替代列表
  时放弃该条件。短于三个字节的替代项可能使整组不能用于索引筛选。
- 只独立使用必要条件，不把任选分支、可选重复中的某一部分当成全局必要条件。
- 查键预算不足时跳过整组并集，保留此前完成的安全过滤结果。仍有安全结果就
  扫描这些候选文件；没有任何可用条件时才扫描全部已索引文本文件。
- 无论候选是否经过筛选，最终都由原正则验证；预算不限制返回结果条数。
- `-F -i` 先转义固定字符串，再走忽略大小写的正则提取路径。

这些常量也位于普通正则使用的提取路径中，因此实验包含大小写敏感查询对照。
本次没有引入新的大小写归一化索引、索引格式、命令行开关或运行时调参接口。
扫参时使用的环境变量只存在于临时实验构建中。

## 4. 环境、数据集与统计口径

| 项目 | 记录 |
|---|---|
| 硬件 | Apple M5，10 个逻辑 CPU，24 GiB RAM |
| 系统 | macOS 26.6.2，build 25G83 |
| 工具 | Rust 1.94.0，ripgrep 15.2.0 |
| 并行设置 | `RAYON_NUM_THREADS` 未设置，使用默认值 |
| coderg 起始提交 | `bdedff2affe7901c566ded4e2551d64c0a87ab1e`，索引优化及参数变化以源码差异归档 |
| vLLM 提交 | `569adb5a9780f9c02d22a6b29826acf711512356` |
| vLLM Git tree | `d4c097cc8270bbd955b45e6c605a578b0590275e` |
| 语料 | 6,835 个已索引文本文件，86,384,180 字节，82.38 MiB |
| 索引 | 一个 segment；索引目录共 69,627,944 字节，66.40 MiB |

66.40 MiB 是磁盘目录大小，包含当前和缓存 manifest。它既不是搜索进程 RSS，
也不是构建索引的峰值内存。最初三次完整构建耗时分别为 3.30、2.48、2.36 秒，
观测到的最大峰值 RSS 约 2.08 GiB；本决策调整的是查询预算，不解决构建内存。

计时使用热文件缓存，输出普通的“文件名、行号、匹配行”，重定向到 `/dev/null`，
包含进程启动成本。参数实验不使用 `-l` 作为计时输出模式。
默认搜索包含刷新检查；`--no-refresh` 用来更清楚地观察候选规划、索引读取、
文件扫描的成本。在这台机器上，默认模式额外开销通常约为 17 ms。

统计定义如下，后面的表格都按这些定义理解：

- “中位数均值”：先求每个查询的多轮中位数，再对查询等权取算术平均。
- “p95 均值”：先对每个查询按最近秩 `ceil(0.95 × n)` 求 p95，再等权平均。
  31 轮时取第 30 个，101 轮时取第 96 个有序样本。
- “平均峰值 RSS”：默认模式每个查询测三次峰值 RSS，先取查询内中位数，
  再在查询间平均；“最大峰值 RSS”为该组查询和重复中的最大观测值。
- “混合工作负载 p95”：把所有查询的样本等量混合后求 p95，单独列出，不与
  p95 均值混用。这里没有真实用户查询频率数据。
- 置信区间使用查询内按轮次成对重采样的 bootstrap，2,000 次重复，衡量固定
  工作负载上的计时不确定性，不估计跨仓库的泛化能力。

不同配置在同一轮内随机交错执行。`rg --sort path` 只用于完整输出校验，
计时的 `rg` 保留默认并行遍历。输出校验归一化路径开头的 `./`。
macOS 峰值 RSS 用 `/usr/bin/time -l` 采集，该阶段需要在沙箱外执行；后续
101 轮延迟补测没有采集 RSS。不要把不同轮次的绝对耗时当成同轮 A/B 对比。

## 5. 先让 -i 用上索引：主要收益来自这里

以下是引入索引筛选时的独立 A/B，使用最初的 64 / 256 预算，每项 30 轮。
单位 ms，均为默认搜索中位数；这一阶段表内的中位数沿用当时脚本的最近秩定义。

| 查询 | 原先不使用索引筛选的 -i | 引入索引筛选，64 / 256 | rg |
|---|---:|---:|---:|
| AsyncMock 类型名 | 76.71 | 28.57 | 64.13 |
| cuda / rocm 平台名 | 81.20 | 46.37 | 73.99 |

这次大幅改善来自让 `-i` 使用索引。随后从 64 / 256 调到 128 / 128 的收益

该 A/B 共八个查询，另有三个大小写敏感对照；默认、no-refresh 模式均完成

## 6. 参数实验如何进行

### 6.1 粗筛与细扫：63 组不同配置

粗筛为 42 组笛卡尔积：

```text
变体上限：4、8、16、32、64、128
索引键预算：8、16、32、64、128、256、512
```

细扫新增 21 组：

```text
变体 24、48、96 × 键预算 64、96、128、192、256：15 组
变体 32、64、128 × 键预算 96、192：6 组
```

细扫还重复了 32 / 64、32 / 128、64 / 128、64 / 256 四组作对照。
粗筛和细扫均使用八个选择查询、两次预热、七次随机交错计时，主指标是
no-refresh 中位数均值。七个样本的最近秩 p95 就是最大值，不用于判断尾延迟。

为了避免 63 次重编译，扫参使用隔离的 release 实验构建，通过临时环境变量
调整两项预算。诊断记录实际键数、跳过的条件组数、候选文件数和候选字节数；
打印诊断的运行不计入计时。所有配置均校验完整输出和查键硬上限。

粗筛中 64 / 128 暂时领先；细扫中 48 / 128 暂时领先。两次领先幅度都很小，
因此没有直接把扫参排序第一名设为默认值。

### 6.2 六组正式构建复测

以下六组重新编译为不带实验环境变量、诊断代码的正式常量版本：

```text
32 / 64、32 / 128、48 / 128、64 / 128、128 / 128、64 / 256
```

每个查询 / 配置 / 模式预热三次、随机交错计时 31 次。除了八个选择查询，
加入六个额外查询和三个大小写敏感对照；默认模式额外采集三次 RSS。

下表汇总 14 个忽略大小写查询，时间单位 ms，内存单位 MiB：

| 配置 | 默认中位数均值 | no-refresh 中位数均值 | 平均峰值 RSS | 最大峰值 RSS | 平均实际键数 |
|---|---:|---:|---:|---:|---:|
| 32 / 64 | 45.719 | 28.553 | 24.70 | 27.41 | 41.4 |
| 32 / 128 | 45.521 | 28.475 | 25.17 | 28.81 | 59.9 |
| 48 / 128 | 44.050 | 26.897 | 25.47 | 29.11 | 69.0 |
| 64 / 128 | 42.821 | 25.573 | 25.05 | 28.34 | 77.1 |
| **128 / 128** | **42.614** | **25.484** | **24.82** | **27.80** | **83.4** |
| 64 / 256，初始默认 | 42.925 | 25.737 | 25.41 | 29.55 | 90.6 |

128 / 128 相对初始默认的中位数均值改善为 0.73% / 0.98%
（默认 / no-refresh）；对应 95% 区间约为 0.29%–1.09% / 0.22%–1.39%。

在八个选择查询上，128 / 128 为 41.190 / 24.058 ms；在六个额外查询上，
为 44.512 / 27.385 ms。初始默认对应为 41.575 / 24.452 ms 和

额外查询对选择有实际影响：

- tensor 分配调用：48 / 128 约 60 ms，128 / 128 约 49 ms。

因此 32 / 128、48 / 128 在选择集上看起来接近，并不足以支持设为默认。
最终选择参考了额外查询，这六个查询不再是最终配置的完全独立测试集。

用户继续询问 p95 和 128 / 256 的代价，因此补测了当前 128 / 128 与
128 / 256。两者只改变 `MAX_INDEX_LOOKUPS`，使用正式 release 二进制。
14 个查询各预热五次，每项 / 配置 / 模式测 101 轮，查询顺序和轮内配置顺序

14 个查询中有十个的实际键数和候选文件数都没有变化；主要变化来自

### 6.4 对先前 p95 结论的澄清

31 轮复测中，64 / 256 → 128 / 128 的默认 p95 均值为 44.818 → 44.025 ms，
点估计下降 0.792 ms（1.77%）；no-refresh 为 27.303 → 27.254 ms，下降

101 轮补测另算的等频混合工作负载 p95 为 59.471 → 59.587 ms（默认）、
43.161 → 42.686 ms（no-refresh）。这与各查询 p95 均值是不同统计量，
也不代表真实用户的请求分布。

旧样本重分析见 [previous-p95.json](https://github.com/b1indsight/coderg/blob/5ca67a2470ac9e9e3b7cc08ad3f2b8115f68a170/benches/results/data/vllm-case-budget-2026-09-07/key256/previous-p95.json)。

## 7. 内存差距：实测与估算分开

| 配置 | 平均峰值 RSS，MiB | 最大峰值 RSS，MiB | 依据 |
|---|---:|---:|---|
| 64 / 128 | 25.05 | 28.34 | 31 轮复测阶段另做的三次 RSS 采样 |
| 64 / 256 | 25.41 | 29.55 | 同上 |
| 128 / 128 | 24.82 | 27.80 | 同上 |
| 128 / 256 | 约 25.5–26.5 | 约 30–32 | 粗估，尚未做相同协议的 RSS 实测 |

估算依据是：提高到 256 个键只使四个查询增加实际键数；已有 64 / 256 与
128 / 128 的对照中，长标识符查询多读约 124 个键时，峰值 RSS 多约 3.47 MiB。
结合这四个查询的实际读取变化，估计总体平均差约 1 MiB，少数查询差几 MiB。

这个估算不是置信区间，也不是内存上界，不能当成 128 / 256 的已测结果。
总 RSS 还包括 manifest、内存映射驻留页、倒排列表、集合、正则和文件扫描缓冲；
查键预算加倍不会让这些部分按同一比例增长。

三组主要配置之间的内存差距不足以单独决定选择。索引格式和文件完全复用，
所有实验后的索引文件 SHA-256 均未改变，目录大小保持 66.40 MiB。

## 8. 选择原因与未选方案

1. **首先保证完整匹配。**采用安全提取、完整并集、必要条件交集和最终正则
   验证。预算只能降低过滤能力，不能删掉合法分支或限制返回结果。
2. **保留 128 个变体。**较小预算在普通多分支、类定义查询上出现明显退化；
   64 / 128 与 128 / 128 很接近，后者在正式复测的综合中位数表现略好。
3. **把查键上限留在 128。**与 128 / 256 的直接对比里，中位数略快，几个常见
   查询有约 1–1.5 ms 的差距，扩大预算没有带来足够的总体收益。
4. **不把 p95 优势作为理由。**目前没有证据证明两者有稳定的 p95 差异。
5. **内存作为次要因素。**实测和估算都表明差距小，不需要为省约 1 MiB 牺牲
   明确的查询收益；当前没有发现需要这种取舍的收益。
6. **保持部署简单。**已有索引直接可用，当前实现和默认值已经过正确性验证。

未采用更小变体预算，因为 8 / 16 个变体即使配 256 个键，也使八个选择查询中
四个回退到全量扫描，no-refresh 均值约 40 ms，而较好配置约 24 ms。
32 / 48 的回退或过滤不足则被额外查询暴露。

未采用 512 个键，因为粗筛没有看到整体收益：64 个变体时，128 / 256 / 512
键的 no-refresh 中位数均值分别约为 24.15 / 24.30 / 24.48 ms。
这只是该轮粗筛证据，不是所有查询上更大预算必定更慢的断言。

## 10. 局限与重新评估的条件

当前证据来自一台机器、一个 vLLM 提交、热缓存和人工选择的常见查询，
没有覆盖冷缓存、多仓库、持续高并发、交互终端的大量输出或真实查询频率。
最大观测 RSS 不是内存上限；计时区间不代表对未知仓库的保证。

扫参没有测试超过 128 个变体；128 / 128 在六个正式复测配置中综合表现最好，
不意味着 63 个配置在所有验证查询上都做过同等规模的比较，更不意味着穷举了
整个参数空间。多个配置处在接近的平台区间。

以下情况值得重新开实验，而不是直接调大数值：

- 真实常用查询反复触及预算，诊断显示大量候选可以由额外完整条件排除。
- 在更多仓库、语言或 Unicode / 多分支查询上出现可重复的退化。
- 语料规模、索引组织、gram 选择、条件排序或倒排列表处理方式明显变化。
- 对冷启动、尾延迟或并发总内存提出新的目标。
- 需要把条件组数量上限与索引读取上限拆开，分别判断它们的成本。

重新评估时，应保持相同输出语义和完整结果验证，记录实际键数、候选文件及
字节数，同时测默认与 no-refresh。应在同一轮随机交错对照，重复测量确认
收益，并明确 RSS 是实测还是估算。若真实场景证明 256 个键能稳定获益，可以
再调整；当前没有必要提前为这些尚未观察到的场景支付额外索引处理成本。

仅复核 101 轮补测的核心数值，无需语料或编译，可在仓库根目录执行：

```sh
python3 - <<'PY'
import json
import statistics
from pathlib import Path

path = Path('benches/results/data/vllm-case-budget-2026-09-07/key256/results.json')
rows = json.loads(path.read_text())['queries']
for mode in ['default', 'norefresh']:
    for config in ['v128-k128', 'v128-k256']:
        key = f'{config}/{mode}'
        p50 = statistics.mean(row['variants'][key]['median_ms'] for row in rows)
        p95 = statistics.mean(row['variants'][key]['p95_ms'] for row in rows)
        print(mode, config, f'p50 mean={p50:.3f} ms', f'p95 mean={p95:.3f} ms')
PY
```
