# nextMask 与 sparse covering：保留实验，暂不采用

日期：2026-09-14。状态：暂不接入默认搜索或索引维护流程。

实验分支保留为 `experiment/nextmask-false-positive-profile`。主分支保留方案、测量记录和复现资料；不合入实验 bench、查询执行器、测试入口或 mask 存储格式。对照基线为 `a517489`，实验期间生产 `src/` 与主分支一致。

## 方案

每个 `(trigram, 文件)` 记录一个 8-bit nextMask。遍历该 trigram 的所有出现位置，将紧随其后的字节映射到一个 bit 并 OR 累计；EOF 不贡献 bit。查询 literal 中存在确定的下一字节时，检查对应 bit。当前映射为 `1 << (ngram::hash(&[byte]) & 7)`，是一个哈希函数、8 个 bit 的近似过滤器，存在碰撞。

实验比较两种用法：

- **原 covering 加 mask**：保留原有 posting 条件，再在条件内过滤。对于同一组已执行的条件，候选只减不增。
- **masked covering**：让 trigram 的 key 长度仍为 3，覆盖长度视为 4，与真实 sparse grams 一起选择；同长优先真实长 gram。允许省掉部分 posting，因此候选不保证是原候选的子集。

例如 `rocm` 原条件是 `posting(roc) ∩ posting(ocm)`，新 covering 可改成 `posting(roc) ∩ mask(m)`。当前 `m` 和 `e` 的 bit 相同，只有 `process` 的文件也能通过新条件，而原来的 `ocm` 能将其排除。覆盖四字节不等于精确 4-gram 的过滤能力。

执行器保留正则必要组之间的 AND、分支之间的 OR、分支内部条件之间的 AND；全局最多读取 128 个不同物理 key。原始 posting 按 key 缓存，mask 结果按完整条件缓存，避免不同下一字节或 trigram 哈希碰撞混用结果。预算不足时放宽过滤，不能截断 OR 导致漏报。

## 搜索结果

[48 项 covering 对照](https://github.com/b1indsight/coderg/blob/5ca67a2470ac9e9e3b7cc08ad3f2b8115f68a170/benches/results/masked-cover-2026-09-14.md)使用固定 vLLM 与 Chromium 语料，比较原 covering、原 covering 加 mask、新 masked covering。每项均核对完整逐文件匹配行数。

| 新 covering 相对基线 | vLLM，34 项 | Chromium，14 项 |
|---|---:|---:|
| 实际 posting key 查询次数 | −8.9% | −11.2% |
| 候选文件数 | +4.9% | −2.5% |
| 倒排阶段耗时合计 | +1.0%，基本持平 | −6.7% |

合计为逐查询中位数之和，不是完整 CLI 延迟。mask 在计时前准备并常驻内存，没有包含落盘和加载成本。

- vLLM `rocm`：误报文件 1 → 1,800，读取＋匹配耗时 4.74 → 19.99 ms。
- Chromium 类声明：posting 次数 4 → 3，但返回 ID 更多，倒排耗时 34.77 → 54.77 ms。
- Chromium `test`：posting 次数 2 → 1，倒排耗时 39.78 → 14.63 ms。

另测[指定 OR 正则](https://github.com/b1indsight/coderg/blob/5ca67a2470ac9e9e3b7cc08ad3f2b8115f68a170/benches/results/search-or-2026-09-14.md)：


区分大小写，`.` 保留正则语义。两份语料的 posting 次数均从 30 降到 21；倒排与扫描阶段中位数之和约降低 16%。这是单条受益查询，且两阶段独立计时，不能解释为完整 CLI 或所有查询都加速 16%。

## 更新结果与格式边界

[更新测试](https://github.com/b1indsight/coderg/blob/5ca67a2470ac9e9e3b7cc08ad3f2b8115f68a170/benches/results/mask-update-2026-09-14.md)回放 vLLM 连续 30 个真实 commit，每个独立重复 3 轮，改动 1–27 个文件。现有流程已重新读取和提取修改文件，不存在“gram 集合相同就免写”的优化；mask 在同次读取中额外累计。

| 模式 | 每 commit 刷新耗时中位数 |
|---|---:|
| 主分支 | 49.59 ms |
| 额外计算、排序、序列化 mask | 51.07 ms |
| 再批量写入并同步 mask | 57.94 ms |

按同一个 commit 配对，批量原型增加耗时中位数为 **8.28 ms**，增幅中位数 **14.5%**；30 步合计增加 **15.9%**。配对统计不等于上表总体中位数直接相减或相除。逐文件单独同步的另一组对照更贵，配对增幅中位数为 35.4%。

刷新计时包含状态检查、提取、posting 写入、自动合并和 manifest 发布，不含 Git checkout、索引加载、搜索或验证。批量原型初建 0.849 → 1.004 s，初始逻辑文件大小 72.94 → 113.88 MiB。

上述持久化采用 sidecar：每条记录保存 3 字节精确 trigram 和 1 字节 mask；每批统一同步。它不是最终 posting 内嵌格式，尚未接入查询、垃圾回收、mask 的 segment 合并、跨文件崩溃一致性和额外内存预算。空间和维护成本不能外推为最终方案的精确值或严格上界。

## 决定与重新评估条件

目前没有稳定的整体搜索收益来证明增加格式及维护复杂度值得，因此维持现有主分支流程。搜索和更新的百分比不能直接相抵；实际收益取决于两者的绝对耗时、频率以及查询分布。

后续如重新推进，需要同时满足：

1. 查询规划考虑 posting 长度和过滤能力，避免只按覆盖长度省略必要的精化条件。
2. 在有代表性的查询分布上测得完整搜索收益，包含 mask 的读取与加载；保留退化查询作为对照。
3. 完成一致性、合并和回收设计，再测长期真实更新、索引体积与写入量，而非只测 mask 计算。
