# coderg 与 Cursor 正则搜索设计的剩余差距

截至 2026-09-08，原对比基线为 `main` 的 `7438754`。刷新路径与小仓库线程策略已合并；查询片段覆盖和默认 256 MiB 构建工作缓冲区预算已实现，见[覆盖设计与验证](query-covering.md)、[构建预算与验证](index-build-memory-budget.md)。下一项算法实验是基于语料频率的权重。本文件保留原差距的依据，未实现部分均为后续工作。

对比来源是 Cursor 于 2026-03-23 发布的[《快速正则搜索：为 agent 工具构建文本索引》](https://cursor.com/cn/blog/fast-regex-search)。文章描述设计思路，并未公开完整生产实现，因此需要区分明确的设计差异和 coderg 自身的工程待办。

## 1. 对比范围与当前基础

文章明确描述了查询侧 `build_covering`、基于字符对频率的权重、Git 提交基础层与修改覆盖层，以及编辑器进程内的索引查找。构建时顺序写 postings，排序后的哈希查找表通过 mmap 查询，再按偏移读取 postings。[来源：Cursor 文章的稀疏 N-grams 与本地索引章节](https://cursor.com/cn/blog/fast-regex-search)

coderg 已具备本地倒排索引、稀疏 gram、哈希键、不可变索引段、Git 状态复用、增量更新，以及候选文件上的完整正则验证。lookup 和 postings 均采用 mmap，按需解码相关列表；同时映射两个文件不等于将它们全部读入物理内存，不能仅据此判断内存效率优劣。实现细节见[已实现的优化与策略](implemented-optimizations.md)。

此前已完成的刷新优化包括逐 visitor 批次收集、并行合并后的排序、manifest 字节切片解析，以及历史快照不超过 512 个文件时串行遍历。它们降低了已有流程的成本，当时查询片段选择仍沿用原来的算法。见[刷新路径优化文档](refresh-path-optimization.md)。

| 项目 | coderg 当前状态 | 差距性质 | 建议顺序 |
|---|---|---|---|
| 查询片段覆盖 | 已增加多个覆盖 gram；保留分支内部求交，按候选安全停止查表 | 第一轮已实现，性能按工作负载验证 | 见[覆盖设计](query-covering.md) |
| 字符对权重 | 确定性的混合函数，没有语料频率信息 | 明确的算法差异 | 第二轮 |
| 跨查询状态复用 | 每次 CLI 搜索重新加载索引并检查文件快照 | 与编辑器集成方式不同；事件机制待设计 | 按连续搜索需求推进 |
| 构建内存上限 | 已加入默认 256 MiB 工作缓冲区预算、分块提取和磁盘外排 | 主要缓冲区已限制；非硬性 RSS 上限，对方完整策略未知 | 见[预算与验证](index-build-memory-budget.md) |
| 索引维护与并发写入 | 段数阈值触发重建，无历史缓存 GC 和跨进程写锁 | coderg 工程待办；对方细节未知 | 按长期运行和并发需求推进 |

## 2. 查询覆盖：从一个最长 gram 到多个必要片段

原基线的 `best_hash` 枚举字面量中的可用 gram，选择最长的一个；同长度时由后遇到的替换。这里的“最长”是启发式，并不代表倒排列表最短。固定字符串搜索只生成一个这样的过滤条件；正则搜索可以从多个必要片段得到多个条件，因此也不能说整个正则查询永远只查一个 gram。

本轮 `covering_hashes` 保留每个字面量的最长键并补充覆盖片段。后续提取规则经历了[固定字面量优先](../benches/results/fixed-literal-extraction-2026-09-08.md)和[统一组合预算](../benches/results/small-variant-extraction-2026-09-08.md)两轮实验。当前第一遍的单字符类上限为 16，整体组合上限恢复为 128；没有可用条件时以 128 / 128 重试。最新的[分支覆盖实验](../benches/results/branch-covering-2026-09-08.md)保留分支内部求交，先做完整初筛，再按当前候选细化并安全停止无效查表。具体实现见[覆盖设计与验证](query-covering.md)。

单个 gram 无法约束字面量其余部分。若很多文件共享选中的片段，即使完整字符串罕见，也会读入较多候选文件。覆盖算法的目标是用少量互补片段约束更多查询内容；增加的查表和求交成本是否值得，需要由候选读取的节省来证明。

建议先在现有索引上实现覆盖选择，保持 gram 生成规则与哈希不变。查询只能选择当前索引保证包含的键：现有索引包含全部 trigram 和长度 4–24 字节的稀疏 gram，不能直接查询未建索引的两字节片段或更长片段。满足这个条件时，可以单独验证查询改动，无需更换索引格式。

多片段查询还需要保留正则分支的逻辑。例如，两个可选字面量分别产生必要片段 A、B 与 C、D，其候选逻辑应为：

```text
(postings(A) ∩ postings(B)) ∪ (postings(C) ∩ postings(D))
```

不能把它改成四个列表直接求交，否则会漏掉只匹配其中一个分支的文件。当前查询结构已支持组间求交、组内分支求并、分支内部求交；旧版按序号混合分支的保守近似保留在历史报告中。

现有上限为每个提取片段最多 128 个字面量变体、每次查询最多读取 128 个不同索引键。覆盖方案必须继续控制预算；超预算时只能放宽过滤，不能截断可选分支。当前预算处理见 [intersect_postings](../src/search.rs#L128)。

这一轮应同时记录候选文件数、候选总字节数、查表键数、postings 解码量、集合运算时间及完整搜索延迟。候选更少本身不构成性能结论。还要检查短字面量、重复字节、大小写变体、分支和无可用片段时的回退，确保相对于全扫描没有漏报。

## 3. 权重：让片段边界反映代码语料的频率

当前 [pair_weight_value](../src/ngram.rs#L126) 对两字节值执行固定的混合函数。它保证构建和查询结果一致，但不利用哪些字节对在代码里更常见的信息。稀疏 gram 的边界由权重决定，因此权重会影响最终键集合、posting 长度和候选范围。

可以用代表性代码语料统计字节对频率，生成固定权重表，再与现有权重比较。训练语料应与评估仓库分开，覆盖多种语言和文件类型；稀有频率相同、未见过的字节对也需要确定性的排序规则。

这里有两个不同的优化维度：字节对频率影响哪些 gram 被建入索引；实际 posting 长度影响一次查询优先处理哪些已存在的键。前者不能代替后者。当前会利用已缓存 posting 的文件数调整分支与分支内的处理顺序；未知 key 仍保持覆盖顺序，解码前的全局成本预测可另行评估。

更换权重会改变稀疏 gram 集合。实现时需要记录权重版本并重建索引，或者提供明确兼容策略；查询端直接套用新表读取旧索引会有漏报风险。

验收应包含建索引时间、峰值 RSS、索引体积、posting 分布和跨语料搜索延迟。先固定现有权重测试覆盖，再固定覆盖方案测试权重，可以分辨收益来自哪一项。

## 4. 状态复用：减少重复加载，并设计增量变化来源

当前 [search::run](../src/search.rs#L42) 每次加载 manifest 和索引段，默认随后执行刷新。即使 Git HEAD 和 tree 未变，仍通过 [collect_files](../src/index.rs#L596) 枚举目录、读取文件元数据并比较快照。串行策略降低了小仓库开销，但没有减少检查的文件数量。

常驻服务或编辑器集成可以复用 manifest、索引映射和线程池。进一步减少全量遍历，则需要持续、可靠的变化来源，例如文件事件与已知编辑操作，并为每次搜索定义“哪些修改已经纳入索引”的边界。

这是两个可分开验证的阶段：先测量仅复用进程内状态的收益，再引入事件驱动更新。事件队列溢出、服务重启、ignore 规则变化和 Git 切换都需要重新同步的路径；已有文件原地修改通常不会改变父目录 mtime，单靠目录属性无法代替变化检测。

当前 `--no-refresh` 会跳过同步，但仍加载索引，并使用旧候选读取文件当前内容；它可能漏掉修改后新增的匹配。因此只能在确认索引新鲜的 benchmark 中用于隔离刷新成本，不能直接作为事件驱动刷新方案。当前长度与 mtime 快照本身也无法识别两者均保持不变的内容替换，详见[现有边界](implemented-optimizations.md)。

性能评估应区分首次启动、连续查询、单文件编辑后立即查询、大量修改后的同步，以及事件丢失后的恢复。除延迟外，还要记录服务常驻内存，避免只报告复用带来的耗时下降。

## 5. 构建内存：已加入 256 MiB 工作缓冲区预算

原基线先逐文件提取 gram，再整体排序关联记录，仍需保存全语料记录。2026-09-08 已改为 32 KiB 分块提取、有限并行队列、预算内记录排序及超预算外排。中间归并每组最多 32 个 run，最终按 gram 范围最多 4 个任务并行归并并编码 postings，再生成 lookup，省去最终原始有序 run 的写读，仍输出同格式索引段。[4 路归并实测](../benches/results/parallel-merge-2026-09-08.md)。全量构建和增量刷新默认使用 `--build-memory-mib 256`，可按命令调整。

预算覆盖内容块、gram 临时集合、排序记录、归并和流式段编码缓冲；不直接限制文件元数据、Git 库状态、分配器保留页面及 mmap 驻留页，因此不能称为进程 RSS 硬上限。Cursor 未公开完整构建预算策略，不能据此比较双方峰值内存。

设计、边界及失败清理见[构建预算文档](index-build-memory-budget.md)；峰值 RSS、构建耗时、临时写入量及更大语料结果见[本轮 benchmark](../benches/results/build-memory-budget-2026-09-08.md)。

## 6. 索引维护：压实、缓存回收与多进程写入

当前 `MAX_SEGMENTS = 8` 控制活动段增长。在适用的变更刷新分支中，达到段数阈值或发生较大变更时会重建；未变化的快照会提前返回，并不是一到八段就立即重建。历史段和 Git tree manifest 没有按容量或存活引用进行回收。见 [refresh](../src/index.rs#L204)。

后续可以评估合并已有索引段，只保留当前有效文档版本，降低重复从源码提取 gram 的成本。历史缓存 GC 则需要同时考虑当前 manifest、保留的 Git tree 缓存以及仍在使用旧段的查询，不能简单删除当前 manifest 未引用的文件。

多进程同时刷新也需要明确的写入协调。当前 [write_manifest_file](../src/index.rs#L559) 使用固定的 `.json.tmp` 临时路径，代码没有跨进程写锁。临时文件替换有助于发布单次更新，但不能解决两个写者基于不同快照更新和覆盖结果的问题。

建议先建立单写者约束、明确的提交顺序和失败恢复，再考虑后台压实与回收。验证应覆盖两个进程同时刷新、写入中断、旧读者跨越新版本发布，以及缓存回收后的 Git 切换。

## 7. 其他边界与不能确认的结论

下面几项需要保留在对比记录中，但应按各自证据判断：

| 项目 | 当前事实与处理建议 |
|---|---|
| gram 长度和组成 | coderg 明确采用全部 trigram 加 4–24 字节稀疏 gram。可实验调整，但应联合测量构建成本、体积和查询选择性 |
| posting 执行成本 | 相关列表解码成 `Vec<u32>`，查询缓存后通过 `BTreeSet` 做并集和交集。覆盖查询增加列表数后，再评估有序列表运算或其他表示的收益 |
| `-l` 的提前停止 | 当前仍建立行号索引并遍历匹配；可单独优化找到首个匹配后的返回，见 [match_file](../src/search.rs#L167) |
| 与 rg 的语义兼容 | 整文件匹配在跨行空白和空匹配上仍有已知差异；需要单独明确兼容目标，不能归因于索引过滤 |

文章没有披露生产 gram 长度上限、具体 watcher/daemon 机制、构建硬性内存预算、写锁和 GC 策略。它介绍的 Bloom 位置与后继掩码属于 Blackbird 历史方案，也不能直接列为 Cursor 当前能力。以上公开信息不足以证明 Cursor 完全不遍历目录，或已经解决了本文列出的全部工程待办。[依据：Cursor 原文](https://cursor.com/cn/blog/fast-regex-search)

## 8. 下一轮实验与已有证据

第一轮已只改变查询覆盖，保持权重、索引格式和刷新策略不变。对照组使用本文基线，在相同索引上比较默认搜索与 `--no-refresh`，分别观察完整使用成本和查询阶段收益。110 项新旧输出一致；共享最长片段的定向查询有明显收益，原有矩阵没有显示普遍加速，详情及回退见[覆盖性能报告](../benches/results/query-covering-2026-09-08.md)。第二轮再评估固定频率表，并将重建成本计入结果。

沿用现有真实仓库与合成语料矩阵，覆盖长短字面量、常见与罕见片段、正则分支、大小写、无匹配和大量输出。计时继续随机交错运行，在计时外校验完整输出；同时报告中位数、p95 和波动区间。若增加常驻服务实验，应单列连续调用结果，避免与新 CLI 进程的计时混合。

现有[小仓库线程策略 benchmark](../benches/results/small-repo-threads-2026-09-07.md)中，100 项与 rg 输出一致的查询有 90 项中位数低于 rg；总计 102 项中另外两项存在已知语义差异。64 个大文件的语料汇总仍慢于 rg。这些数据支持继续按工作负载定位成本，不能推算与 Cursor 的性能差距，也不是尚未实现的覆盖或频率方案的收益证据。
