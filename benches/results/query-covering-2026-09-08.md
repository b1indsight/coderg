# 多片段查询覆盖：2026-09-08 实验

版本说明：本报告记录最初的查询覆盖版本。随后已根据装饰器查询分析，修改为固定字面量优先提取，并完成[单独的性能对比](fixed-literal-extraction-2026-09-08.md)。下面的 key 数、候选数、耗时和测试通过记录均对应修正前版本。

本轮实现保留原来的最长 gram，并增加覆盖字面量其余部分的必要条件。共享最长片段的定向语料有明显收益；既有真实仓库和合成矩阵没有显示普遍加速，部分查询新增的查表与集合运算成本超过候选读取节省。实现及分支保守近似见[设计文档](../../docs/query-covering.md)。

## 方法与正确性

基线是 `74387541f37851bd8df570b9663a507912178909`，新版本为本次工作区实现。Apple M5、24 GiB、macOS 26.6.2、Rust 1.94.0；机器、源文件和二进制哈希均记录在[metadata](data/query-covering-2026-09-08/metadata.json)中。默认线程策略不变。

复用 `benches/refresh_matrix.py`，每项预热 3 轮、计时 21 轮，随机交错运行基线、新版本、两者的 `--no-refresh` 和 rg。每次搜索启动新 CLI 进程，使用热缓存和冻结语料；同一语料的所有搜索共用基线创建的索引。输出校验在计时外完成。原始数据包含每次计时、中位数、p95 和最小值，本文表格是单机描述性结果，没有把小幅差异解释成显著收益或回退。

- 原有 7 组语料共 102 项查询，新旧输出 102/102 一致；其中 100 项与 rg 一致，另外两项仍是基线已知的匹配语义差异。
- 新增共享片段语料 8 项查询，新旧版本及 rg 的输出全部一致。
- 8 组语料的新旧构建生成完全相同的索引段字节；所有搜索完成后，语料、共用索引、二进制及源文件校验均通过。
- `cargo test`：24 个单元测试、3 个 CLI 测试、1 个 Git 增量测试通过。`cargo clippy --all-targets -- -D warnings`、`cargo fmt --check`、`git diff --check` 通过。

## 共享最长片段的定向语料

512 个文本文件，共 17,218,986 字节。所有文件包含基线选中的 `CODERG_BENCHMARK_NE`，只有一个文件包含完整的 `CODERG_BENCHMARK_NEEDLE`。该语料刻意放大单键过滤的弱点，用于验证机制，不能代表普通代码仓库。生成器见[fixture.py](data/query-covering-2026-09-08/fixture.py)，固定提交及配置见[targeted-metadata](data/query-covering-2026-09-08/targeted-metadata.json)。

| 查询 | 默认：基线 → 覆盖（ms） | no-refresh：基线 → 覆盖（ms） |
|---|---:|---:|
| 完整字面量，`-F -l` | 8.85 → 5.20 | 7.04 → 3.44 |
| 完整字面量，`-F` | 8.68 → 5.04 | 7.18 → 3.53 |
| `module_7` / `module_23` 正则分支 | 8.80 → 5.39 | 7.17 → 3.82 |
| 常见字面量，`-F -l` | 13.33 → 13.44 | 11.84 → 11.76 |
| 忽略大小写，`-F -i -l` | 5.42 → 5.49 | 3.84 → 3.93 |

完整字面量的默认 `-F -l` 延迟下降 41.3%，查询阶段下降 51.2%。常见字面量没有同样收益；忽略大小写时，原有局部必要条件已经可以过滤候选。

## 候选与 postings 成本

临时插桩运行的全部 110 项查询输出一致，候选数均未增加。[原始诊断数据](data/query-covering-2026-09-08/metrics.json)包含每项 11 轮的完整计数和分阶段时间。以下是代表性结果，箭头为基线 → 覆盖：

| 语料 / 查询 | 候选文件 | 候选字节 | 查表键 | 解码后 ID 数 | 集合与缓存时间（µs） |
|---|---:|---:|---:|---:|---:|
| shared_anchor / rare_files | 512 → 1 | 17,218,986 → 33,653 | 1 → 3 | 512 → 514 | 5.21 → 11.29 |
| shared_anchor / common_files | 512 → 512 | 17,218,986 → 17,218,986 | 1 → 4 | 512 → 2,048 | 5.46 → 39.46 |
| vLLM / wide_icase_cache | 3,712 → 2,979 | 69,492,825 → 62,343,357 | 20 → 32 | 5,369 → 10,797 | 51.67 → 195.66 |
| vLLM / class_attention | 976 → 623 | 27,702,567 → 20,852,657 | 2 → 8 | 4,257 → 20,533 | 99.67 → 316.79 |
| vLLM / decorator | 1,348 → 1,348 | 19,287,511 → 19,287,511 | 58 → 122 | 25,283 → 60,326 | 472.00 → 2,191.55 |
| vLLM / cuda_call | 306 → 306 | 7,229,512 → 7,229,512 | 6 → 31 | 313 → 15,968 | 15.71 → 319.29 |

`rare_files` 的过滤总时间从 25.71 增到 32.17 µs，但候选读取量下降约 99.8%，足以抵消开销。`decorator` 的候选不变，过滤总时间从 1.26 增到 3.84 ms，解释了完整搜索的回退。当前实现没有根据实际 posting 长度决定是否值得增加某个覆盖条件，这是后续成本控制的明确方向。

集合与缓存时间为整个候选过滤时间减去 `DiskIndex::postings` 调用时间，包含预算检查和缓存管理；ID 数是该调用返回的有效 ID 数，不能当作磁盘读取字节量。诊断语料使用单基础段，因此不涉及旧版本 ID 的过滤损耗。规划耗时也有增加，例如共享片段 `rare_files` 从 0.63 到 2.83 µs，vLLM `decorator` 从 67.38 到 104.00 µs。

## 复现与数据

主计时命令使用 `--iterations 21 --warmup 3 --build-iterations 1 --rss-runs 0`；基线和新版本均为 release 构建。完整路径、二进制哈希、语料提交、查询参数及各轮数据保存在原始 JSON 中。[逐查询中位数 CSV](data/query-covering-2026-09-08/per-query.csv)汇总所有 110 项查询。

诊断命令为：

```sh
python3 benches/query_cover_metrics.py --baseline-ref 7438754 \
  --plan /private/tmp/coderg-query-cover-8__b1tet/metrics-plan.json \
  --output /private/tmp/coderg-query-cover-8__b1tet/diagnostics --iterations 11
```

诊断脚本在临时源码副本中增加计数和计时，基线与新版本共用基线索引，每项预热 1 轮、随机交错测量 11 轮并核对输出。插桩可执行文件不用于上面的完整 CLI 延迟结论。重新运行时，应从两份 metadata 的 `plan.datasets` 合并得到计划，并把冻结语料路径替换为本机路径。
