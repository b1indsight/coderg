# 索引构建耗时瓶颈 — 2026-09-08

**少量大文件首先受文件级提取并行限制；提取内部的热点是 gram 扫描与 HashSet 插入。** 同样的 64 MiB 内容，64 个文件构建约 147 ms，8 个文件约 145 ms，合成一个文件则约 593 ms。单文件的提取与收集阶段占构建时间约 95%。vLLM 等产生外排的语料还有另一处瓶颈：串行归并与最终编码合计约占 40%。

本次测量当前正式实现，构建缓冲预算 256 MiB，未设置 `RAYON_NUM_THREADS`。本机 Rayon 池为 10 线程，提取线程数为 `min(8, 文件数)`，因此单个文件只由一个提取线程处理。上轮[共用池 4–6 线程原型](build-thread-count-2026-09-08.md)不在此次分项测量范围内。

## 方法与校验

- Apple M5，10 个逻辑 CPU，24 GiB RAM，macOS 26.6.2，Rust 1.94.0。
- 每组语料、每个版本预热 2 次，正式测量 7 次；随机交错正式 release 二进制与插桩版本，每次启动新进程、新建索引。计时包含进程启动和完整构建，不含索引校验及测试目录清理。
- 插桩只加入独立源码副本；使用仓库已有 `profiling` profile，继承 release 优化并保留调试信息。插桩版本相对正式版的耗时中位数变化为 −1.1% 至 +2.3%，分项用于定位热点，不作为优化收益。
- 计时在沙箱内执行；调用栈采样因系统权限限制在沙箱外执行，两者独立运行。没有同时运行其他 benchmark 或编译。预热后的文件系统状态用于比较，但未强制锁定所有输入页驻留内存，也未测试冷缓存。
- **90 次构建全部通过索引段字节与文档元数据一致性校验**，比较范围为相同语料的正式版和插桩版；插桩副本的现有 **47 项测试通过**。各组不同文件布局的索引本就不同，不跨布局比较索引字节。
- 分项用 `Instant` 墙钟计时：主线程阶段可反映关键路径；工作线程计时是所有线程的累计值，包含被调度出去的时间，不能相加后当成完整构建耗时。另用子进程 user/system CPU 时间计算平均用核数。

## 相同输入，改变文件数

原始 `few_large_64` 是 64 个各 1,048,576 字节的合成 Rust 文件，每个 8,210–8,340 行，共 **527,380 行**。按路径顺序原样拼接为 8 个 8 MiB 文件及 1 个 64 MiB 文件，拼接后的总字节 SHA-256 一致。[生成脚本](data/build-bottlenecks-2026-09-08/group_corpus.py)和[逐文件来源](data/build-bottlenecks-2026-09-08/corpus-provenance.json)已保存。

下表为无插桩正式版本的耗时：

| 输入布局 | 总大小 | 提取线程 | 完整构建中位数 | 最小–最大 | 平均用核数中位数 |
|---|---:|---:|---:|---:|---:|
| 64 × 1 MiB | 64 MiB | 8 | 147.49 ms | 144.98–148.30 ms | 6.80 |
| 8 × 8 MiB | 64 MiB | 8 | 144.51 ms | 138.41–152.13 ms | 6.70 |
| 1 × 64 MiB | 64 MiB | 1 | 593.48 ms | 592.32–594.47 ms | 1.18 |

文件布局也会改变 docid、分块边界和去重比例，因此总耗时倍率不是严格的纯并行加速比。不过分项直接显示：单文件的提取阶段变慢，后续排序与编码反而更快。

插桩后的阶段中位数如下，单位 ms。排序、去重、编码都是“提取结束后处理”的子项，不能再和该父项相加；各列取独立中位数，也不会严格相加等于总计。

| 阶段 | 64 × 1 MiB | 8 × 8 MiB | 1 × 64 MiB |
|---|---:|---:|---:|
| 构建函数总计 | 145.42 | 143.39 | 594.75 |
| 提取与收集 | 104.68 | 110.86 | 567.35 |
| 其中：收集线程等待结果 | 94.66 | 101.17 | 559.82 |
| 提取结束后处理 | 35.83 | 28.88 | 23.17 |
| 其中：排序 | 23.54 | 20.18 | 16.89 |
| 其中：排序后去重 | 3.00 | 3.35 | 3.27 |
| 其中：最终编码与写入 | 7.71 | 4.30 | 2.87 |
| 临时文件写入 / 归并 | 0 / 0 | 0 / 0 | 0 / 0 |

64 文件组中，提取与收集占构建约 72%，收集线程约 90% 的时间等待提取结果。8 个提取线程累计 gram 扫描与块内 HashSet 去重 729.32 ms、HashSet 转 Vec 56.18 ms、读取 7.66 ms、通道发送 5.65 ms。这里只将这些数字用于比较提取内部各项成本，不能把 729 ms 当成整次构建耗时。

单文件组的提取与收集占构建约 95%，收集线程约 99% 的时间等待。唯一的提取线程花费 508.84 ms 生成 gram 并做块内 HashSet 去重、49.01 ms 转 Vec、5.52 ms 读取。当前 `index_files` 按文件分配任务，`hash_file_chunks` 在同一个线程顺序处理该文件的 4,102 个块，因此有空闲线程也不能并行提取这个文件。

重复记录确实存在：64 文件组排序输入 7,335,895 条，去重后 3,211,895 条，减少 56.2%；单文件组 7,323,817 条变成 530,475 条，减少 92.8%。但这两组都没有外排，单文件排序和去重总计仅约 20 ms，不能解释其约 593 ms 的构建耗时。

## vLLM 与外排阶段

vLLM 为 6,835 个可搜索文件、82.38 MiB；四倍语料为 27,340 个文件、329.53 MiB，来源沿用[构建内存预算实验](build-memory-budget-2026-09-08.md)。以下阶段为插桩中位数，单位 ms；第一行是无插桩版本的完整进程耗时。

| 指标 | vLLM | vLLM ×4 |
|---|---:|---:|
| 正式版完整构建 | 1,251.93 | 5,496.51 |
| 插桩构建函数总计 | 1,232.50 | 5,531.96 |
| 目录与文件状态收集 | 22.61 | 77.50 |
| Git 检查 | 33.10 | 0.08 |
| 提取与收集，含途中外排 | 526.80 | 3,100.02 |
| 提取结束后处理 | 641.93 | 2,301.67 |
| 全程排序累计 | 168.60 | 685.69 |
| 全程排序后去重累计 | 57.32 | 240.59 |
| 全程临时 run 写入累计 | 88.23 | 361.77 |
| 串行 run 归并 | 309.75 | 1,625.48 |
| 最终编码与写入 | 186.95 | 597.90 |
| 初始临时 run 数 | 2 | 8 |

“全程排序 / 去重 / 临时写入”跨越提取期间与提取结束后两个阶段，与父项有重叠，不能把整张表相加。vLLM ×4 是生成目录，没有 Git 仓库，这也是 Git 检查较短的原因。

归并与最终编码合计均约占构建时间 **40%**，其中归并约占 vLLM 的 25%、四倍语料的 29%。这两个阶段在主线程顺序执行，增加提取线程无法直接缩短它们。最终编码计时包括迭代读取、压缩、文件写入与发布，归并计时包括读取、堆合并、去重与临时写入，不能解读为纯算法 CPU 时间。

四倍语料还有明显的读取等待波动：提取线程累计读取时间中位数 3,843 ms，范围 1,054–4,933 ms；正式版总耗时范围 5,214–5,661 ms。这里包含 I/O 等待与调度时间，本轮没有进一步定位到物理磁盘、页缓存或其他系统因素，不能把四倍语料的全部提取耗时都归因于 gram 计算。

## 调用栈与下一步

另对重复完整构建的单个进程使用 macOS `sample`，每组采样 5 秒、请求间隔 1 ms。64 文件组的非等待热点包括 `hashes_for_document`（11,311 个栈顶样本）、HashSet 底层 `HashMap::insert`（7,066）、Rayon 快排递归（3,412）。vLLM 中对应数量为 4,007 / 4,406 / 3,451，同时出现 `PostingsBuilder::write`、run 读取及写入热点。部分函数被内联到调用方，因此不据此细分算法内部百分比。

线程等待栈样本很多，尤其是提取时闲置的 Rayon 工作线程；它们不是 CPU 消耗，不能用全部线程的样本总数计算端到端耗时占比。[采样摘要](data/build-bottlenecks-2026-09-08/sample-summary.json)和[完整调用栈压缩包](data/build-bottlenecks-2026-09-08/samples.tar.gz)已归档，采样时的耗时不混入前面的延迟数据。

针对少量大文件，优先验证**把大文件的块变成可并行任务**，同时保留 23 字节边界重叠与受预算约束的在途任务数。其次再评估 gram 扫描、HashSet 插入及集合转 Vec 的成本。对于 vLLM 规模的仓库，还应单独评估归并与最终编码；继续只调提取线程数会受到这部分串行耗时限制。以上是下一轮实验方向，本轮没有验证它们能带来多少加速。

## 复现材料

数据目录保存了 [原始计时](data/build-bottlenecks-2026-09-08/results.json)、[文件布局补测](data/build-bottlenecks-2026-09-08/grouped-results.json)、[汇总](data/build-bottlenecks-2026-09-08/summary.json)、[源码与制品哈希](data/build-bottlenecks-2026-09-08/manifest.json)、正式源码快照、插桩补丁、生成语料脚本和 stderr 日志。

`prepare.py REPO DEST` 创建插桩副本；在副本运行 `cargo build --profile profiling --offline`，再用 `run.py --control RELEASE_BINARY --probe PROFILE_BINARY --corpus NAME=PATH --output NEW_DIRECTORY` 测量。`--sample` 运行重复构建及系统采样，需要 macOS 进程检查权限；`summarize.py INPUT_JSON... --output SUMMARY_JSON` 重算汇总。实际语料路径、每次构建命令和二进制哈希均在原始 JSON 中。
