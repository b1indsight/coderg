# gram 提取：哈希分布与直接输出 — 2026-09-08

已实现两项修改：改善 gram 集合/映射内部的 64 位哈希分布，以及块内去重成功时直接输出到 Vec。**两项合并后，vLLM 和四倍语料的完整构建耗时分别减少 6.3% 和 6.2%；1 MiB、8 MiB 合成文件组的中位数基本持平。** 主要可观测收益来自哈希分布修改，直接输出 Vec 的独立收益较小。

## 实现

1. `IdentityHasher` 改为 `GramHasher`。`write_u32` 使用 `u64::from(value).wrapping_mul(0x9e37_79b9_7f4a_7c15)`，让原本为零的高位具有分布。当前 Rust 标准库使用 hashbrown 0.16.1，在本机 64 位平台取哈希最高 7 位作为桶筛选标记。该映射同时改变桶位置与高位标记，实验没有单独分离两者的贡献；保存的 `u32` gram 键及索引格式不变。
2. `hashes_for_chunk` 在 `seen.insert(hash)` 返回 true 时立即 `hashes.push(hash)`。读取循环直接发送得到的 Vec，不再在块结束后遍历 HashSet 收集数组。此改动省掉一次集合遍历，也引入了提取期间的 Vec 追加和扩容，不能把旧版“HashSet 转 Vec”的全部耗时当成净收益。

集合仍按输入字节数预留容量，每块创建一次；本轮没有引入集合复用或容量调优。16 KiB 分块、23 字节重叠、线程调度、256 MiB 构建缓冲预算和外排流程沿用原实现。原集合提取函数保留为测试 oracle。

实现位于 [ngram.rs](../../src/ngram.rs) 和 [index.rs](../../src/index.rs)。

## 对照方法

- 三个无插桩 release 版本：修改前、只修改哈希分布、两项合并。只改哈希的版本在独立源码副本中编译，工作区保留两项合并的实现。
- Apple M5，10 个逻辑 CPU，24 GiB RAM；相同 Rust 工具链、依赖锁定和 release profile。未设置 `RAYON_NUM_THREADS`，默认 8 个提取线程、10 个 Rayon 排序线程；构建缓冲预算 256 MiB。
- 每组语料、每个版本预热 2 次、计时 7 次，另测 3 次 `/usr/bin/time -l` 峰值 RSS。每轮随机交错版本顺序，固定种子 20260908，每次启动新进程并新建索引。
- 测量在沙箱外执行，未与编译、测试或其他 benchmark 并发。计时包括进程启动和完整构建，索引校验、搜索校验与清理在计时外执行。使用预热后的文件系统状态，不测冷缓存性能；预热和 RSS 运行不计入耗时中位数，未剔除计时样本。
- 1 MiB / 8 MiB 两组的总输入均为 64 MiB、527,380 行；8 MiB 文件各有 65,680–66,720 行。[语料来源](data/build-bottlenecks-2026-09-08/corpus-provenance.json)。vLLM 为 6,835 个可搜索文件、82.38 MiB；四倍语料为 27,340 个文件、329.53 MiB。小仓库 viberwhisper 为 123 个文件、1.30 MiB。

## 完整构建耗时

单位 ms，均为 7 次中位数。负百分比表示耗时减少。

| 语料 | 修改前 | 仅哈希分布 | 两项合并 | 合并相对修改前 |
|---|---:|---:|---:|---:|
| 64 × 1 MiB | 152.85 | 150.58 | 151.58 | −0.8% |
| 8 × 8 MiB | 148.97 | 148.26 | 150.07 | +0.7% |
| vLLM | 1,283.54 | 1,210.29 | 1,202.29 | −6.3% |
| vLLM ×4 | 5,283.55 | 4,976.71 | 4,955.07 | −6.2% |
| viberwhisper | 27.94 | 26.32 | 26.41 | −5.5% |

相对仅修改哈希分布，追加直接输出 Vec 后，五组耗时中位数分别变化 +0.7%、+1.2%、−0.7%、−0.4%、+0.3%。这些差额很小，不能据此宣称第 3 项具有明显的独立加速效果。

| 语料 | 修改前最小–最大 ms | 合并后最小–最大 ms |
|---|---:|---:|
| 64 × 1 MiB | 149.13–155.26 | 149.40–157.65 |
| 8 × 8 MiB | 145.90–151.56 | 146.05–163.51 |
| vLLM | 1,265.12–1,306.23 | 1,185.98–1,258.78 |
| vLLM ×4 | 5,211.89–5,315.06 | 4,899.81–5,045.67 |
| viberwhisper | 26.82–28.42 | 24.90–26.93 |

8 MiB 合并版本含一次 163.51 ms 的计时样本，已保留。vLLM 和四倍语料每轮的合并版本都快于对应修改前版本，配对耗时变化中位数分别为 −6.1% 和 −6.6%。本轮测量完整构建，不重新插桩拆分 gram、排序等阶段，不能将全部收益直接归因于某一个内部函数。

单位 MiB，每个版本另测 3 次。下表为峰值 RSS 的中位数，最后一列是合并版本三次观测中的最大值。

|---|---:|---:|---:|---:|
| 64 × 1 MiB | 68.45 | 68.52 | 68.45 | 68.59 |
| 8 × 8 MiB | 67.67 | 67.59 | 67.69 | 67.75 |
| vLLM | 207.56 | 207.70 | 207.44 | 207.73 |
| vLLM ×4 | 213.22 | 213.53 | 213.42 | 213.86 |
| viberwhisper | 19.50 | 19.61 | 19.80 | 19.84 |

各语料的峰值 RSS 中位数变化不足 0.3 MiB。外排 run 数仍为 vLLM 2 个、四倍语料 8 个，其余语料 0 个。这里验证了本次修改的实测内存，256 MiB 参数仍是工作缓冲预算，不是操作系统强制的 RSS 硬上限。
