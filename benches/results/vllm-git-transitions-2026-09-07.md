# vLLM Git 修改、提交与回退 benchmark — 2026-09-07

在真实 vLLM 的临时克隆中模拟 Git 状态变化后，32 个文件提交后的首次默认搜索，峰值 RSS 中位数由 **48.31 MiB 降至 27.98 MiB**（减少 42.1%），耗时中位数由 **98.84 ms 降至 86.85 ms**（减少 12.1%）。

全部 7 种状态转换的刷新路径、完整输出和段文件内容校验通过。已索引内容的提交、同树空提交及缓存回退均没有新增段；这三种路径的耗时基本持平。

## 环境与样本

- 优化版为 commit `50d15f456e727f9499ac2e48844612f819edce4f` 的 release 二进制；基线为内存优化前的 `18c9cc78c332c38d95d70dfade3ca50d9455f23c`，二进制 SHA-256 与[此前基线](vllm-performance-2026-09-07.md)核对一致。
- Apple M5，10 个逻辑 CPU，24 GiB RAM，macOS arm64；rg 15.2.0。
- 原始 vLLM commit：`569adb5a9780f9c02d22a6b29826acf711512356`；6,835 个文本文件、86,384,180 bytes（82.38 MiB）。只修改脚本创建的临时本地克隆。
- 单文件为 `vllm/sampling_params.py`，修改前 54,941 bytes；批量为 `vllm/config/` 下按路径排序的 32 个 Python 文件，修改前合计 635,178 bytes（620.29 KiB）。均追加一行唯一标记注释。
- 搜索正则为 `\b(?:SamplingParams|CODERG_COMMIT_BENCH_(?:SINGLE|BATCH))\b`，输出文件名、行号和完整匹配行。初始/回退后为 1,348 行，单文件修改后 1,349 行，批量修改后 1,381 行。

## 测量方法

完整流程预热 1 轮，再计时 11 轮，最后独立测量 3 轮峰值 RSS。每轮为两个版本分别构建新索引；每种状态下随机交错两个版本的测量顺序，不并发运行。

```text
初始干净版本 A
  → 修改一个文件但不提交 → 搜索并生成 delta
  → 提交为 B → 搜索并推进 manifest
  → 修改另外 32 个文件，直接提交为 C → 搜索并生成 delta
  → 空提交 D（tree 与 C 相同）→ 搜索并推进 HEAD
  → checkout 初始版本 A → 搜索并复用缓存索引
  → 再次搜索 A
```

计时命令是默认 `coderg search`，包含新鲜度检查、必要的索引更新、manifest 写入/重载以及搜索，stdout 重定向到 `/dev/null`。clone、Git add/commit/checkout、每轮初始建索引、段文件哈希和输出校验不计入阶段耗时。

每阶段先用 rg 获取预期结果，再执行计时命令，最后通过未计时的 `--no-refresh` 完整输出校验更新后的索引。该流程使用热缓存，不能代表冷缓存下提交后的第一次搜索；`--no-refresh` 校验不会提前消费待测的刷新操作。

峰值 RSS 由 macOS `/usr/bin/time -l` 测量，内存样本不混入耗时统计。原始数据保留每轮状态 commit、刷新诊断、命令、输出摘要、段文件大小及 SHA-256。

## 耗时与内存

下表耗时为 11 次测量的中位数，RSS 为 3 次进程峰值的中位数。这里只使用上述一个查询，不能与全正则套件的查询均值直接比较。

| 阶段 | 原版 ms | 优化版 ms | 原版 RSS MiB | 优化版 RSS MiB |
|---|---:|---:|---:|---:|
| 干净工作区搜索 | 31.33 | 30.84 | 15.45 | 15.06 |
| 未提交的单文件修改 | 47.31 | 46.66 | 21.45 | 19.42 |
| 提交已索引内容 | 75.84 | 75.59 | 22.02 | 22.02 |
| 直接提交 32 个文件的修改 | 98.84 | 86.85 | 48.31 | 27.98 |
| 同树空提交 | 60.61 | 60.45 | 21.83 | 21.94 |
| 回退到缓存的初始版本 | 79.59 | 79.33 | 21.89 | 22.02 |
| 回退后的再次搜索 | 31.03 | 30.78 | 15.44 | 15.47 |

收益主要出现在需要生成新 delta 段的批量修改阶段。单文件只有约 54 KiB，编码工作量小，整次搜索更多时间花在文件/Git 状态检查、manifest 处理和匹配上，因此延迟改善有限。

“没有重新索引”仍可能需要 Git 状态检查、写当前 manifest、写树缓存和重载索引。提交已索引内容的 75.59 ms 与缓存回退的 79.33 ms 是这些操作加搜索的总耗时，不是 Git commit/checkout 命令耗时。

## 索引段与目录大小

两种二进制在每个阶段生成的段内容一致，大小相同。以下列出优化版最后一轮快照。

| 阶段 | 活跃段数 | 新增段数 | 活跃索引 MiB | 全目录文件 MiB | 缓存树数 |
|---|---:|---:|---:|---:|---:|
| 干净工作区搜索 | 1 | 0 | 63.885 | 66.402 | 1 |
| 未提交的单文件修改 | 2 | 1 | 63.975 | 66.493 | 1 |
| 提交已索引内容 | 2 | 0 | 63.975 | 69.011 | 2 |
| 直接提交 32 个文件的修改 | 3 | 1 | 64.774 | 72.327 | 3 |
| 同树空提交 | 3 | 0 | 64.774 | 72.327 | 3 |
| 回退到缓存的初始版本 | 1 | 0 | 63.885 | 72.327 | 3 |
| 回退后的再次搜索 | 1 | 0 | 63.885 | 72.327 | 3 |

每个新增段由 lookup 和 postings 两个文件组成。单文件修改新增一个 delta，批量 32 个文件合并为另一个 delta；没有生成全量替代段。

回退后活跃段恢复为 1，活跃索引恢复为 63.885 MiB；全目录仍约 72.327 MiB。原有 delta 和树缓存继续保留，因此切换到旧版本不会自动回收历史磁盘空间。这个行为在两种版本中相同。

## 复现

分别准备优化前后的 release 二进制，并提供干净的相同 vLLM checkout。脚本会创建自己的临时克隆；输出目录必须尚不存在。RSS 测量依赖 macOS。归档脚本若单独使用，应放回 `benches/vllm_git_transitions.py` 的位置，以正确定位 coderg 源码。

```sh
python3 benches/vllm_git_transitions.py \
  --root /path/to/vllm \
  --baseline /path/to/coderg-before \
  --binary target/release/coderg \
  --output /tmp/coderg-git-transition-results \
  --iterations 11 --warmup 1 --rss-runs 3
```
