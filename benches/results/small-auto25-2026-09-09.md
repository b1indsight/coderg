# 小仓库：25% 默认阈值、查询与真实提交更新

> 文档状态（2026-09-10）：历史全仓库分代试验。当前 B < 32 MiB 已恢复增量追加及 8 MiB 重建，本报告的小库合并/同步成本不代表最终实现；见[三档实测](size-tiers-2026-09-10.md)。

> 后续通过 [同步计时与诊断对照](small-sync-profile-2026-09-09.md) 确认：
> 新增的同步落盘是主要回退来源，普通更新约花费 18–19 ms；本文保留初测数据。

默认阈值已改为 **`M >= max(B × 25%, 8 MiB)`**，保留 8 MiB 下限。
本轮复用 viberwhisper、agentflow 的现有冻结快照和各 16 项查询，并补测
100 / 19 个真实提交的更新及历史回退。没有生成模拟提交。

**无变化查询与 main 基本持平；初始构建和真实提交更新更慢。** 25% 与此前
50% 在这两个小仓库上都受 8 MiB 下限控制，没有触发 B+M 合并，维护决策及
每步 B/M 大小完全相同。相对 main 的回退来自本分支已有的构建/更新路径差异，
不能归因于本次把比例从 50% 改为 25%。

查询差异很小，不能据此声称搜索性能提升。32 项查询的新旧版本输出、退出码
均一致，也全部与 rg 一致，覆盖固定字符串、大小写、正则、文件名及计数输出。
新旧版本初始生成的 segment 文件内容哈希也相同。

构建每版测 7 次；查询每项预热 3 次、正式 31 次，固定随机种子交错执行
main、25%、两者 no-refresh 及 rg；另外每项测 3 次峰值 RSS。计时 stdout
重定向到 `/dev/null`，完整输出比对在计时外执行。查询共用固定的 baseline
索引以隔离读取路径差异；初始构建使用各自索引，检查期间源码、索引和二进制
均未变化。快照目录只读，生成索引及临时文件放在项目 `.cache/2026-09-09/`。

## 真实提交更新

viberwhisper 的快照有 114 个 first-parent 历史版本，本轮取最近 100 次更新：
`30460fe0b07f7cb6f18b19ee2b18d2b0dde7cdb6` → `ab1f117d922fe06da6fc2f1f72605ba227ba4233`。
agentflow 的快照共有 20 个版本，测全部 19 次更新：
`e65d534b0efddadfa433770621ca4340786736bf` → `40efd5bcc760bc1aa05029515d2eb46d3dff3c30`。
每个版本使用独立索引，每步轮换版本执行顺序。

| 仓库 / 方案 | 更新中位数 | 更新 p95 | 更新总耗时 | M 内合并次数 | B+M 合并次数 |
|---|---:|---:|---:|---:|---:|
| viberwhisper / main | 9.99 ms | 18.71 ms | 1.08 s | — | — |
| viberwhisper / 50% | 27.75 ms | 43.74 ms | 3.02 s | 28 | 0 |
| viberwhisper / **25%** | **27.90 ms** | **43.87 ms** | **3.02 s** | **28** | **0** |
| agentflow / main | 11.80 ms | 28.43 ms | 0.27 s | — | — |
| agentflow / 50% | 29.89 ms | 58.13 ms | 0.65 s | 4 | 0 |
| agentflow / **25%** | **29.00 ms** | **58.87 ms** | **0.64 s** | **4** | **0** |

main 在两个仓库分别重新构建 B 12 / 2 次；双代版本均未重建 B。小仓库的
main 重建成本本来就低，本轮取消这些重建没有带来更新收益。当前分支还增加了
段文件、manifest 和目录同步落盘等发布工作；尚未单独测量各项成本，不能把
全部回退归因于某一个系统调用。25% 常量只用于增量维护规划，不参与初始构建。

| 正向更新结束时，MiB | viberwhisper 25% | agentflow 25% |
|---|---:|---:|
| B | 0.070 | 0.818 |
| M | 4.512 | 4.852 |
| 更新完成后观测到的最大 M | 5.011 | 5.616 |
| B+M 总段数 | 8 | 7 |
| 整个索引目录（含待回收旧段） | 24.49 | 11.42 |

真实历史起点更早，因此这里的 B 小于对终点快照新建索引得到的 B；两种大小
口径不可混用。8 MiB 下限允许这类小仓库的 M 超过 B，改动比例到 25% 并没有
把它们的 M 控制在 B 的四分之一。本轮保留既定下限，没有进一步调小。

Git 变化文件数中位数 / 最大值为 viberwhisper 6 / 579、agentflow 29 / 56；
计数包括可能被忽略或不可索引的路径，不能当成 coderg 实际索引文件数。
原始记录保留每步 diff 行数、目标版本变化文件完整字节数及 coderg 日志。

更新计时为 checkout 后首次固定字符串文件查询的完整进程耗时，包含刷新、
合并和查询，排除 Git checkout 及初始建索引。viberwhisper 使用 `fn `，
agentflow 使用 `def `。每步状态更新只测一次，表中 p95 是不同提交间的
nearest-rank 分位数。未变化查询在检查点预热 3 次、正式 7 次。

双代版没有使用历史 tree 缓存，按当前 B+M 的有效快照做 diff；这组小仓库
历史切换也比 main 慢。两种阈值在历史切换中均未触发 B+M 合并。

每步更新和切换后，viberwhisper 的 `fn `、`Transcription`、`self`，以及
agentflow 的 `def `、`class `、`review_batch`，均与 rg 对照文件集合及退出码。
共 **1,161 次对照通过**（945 + 216），另有上述 32 项完整查询输出对照通过。
当前阈值下 3 项 compaction 定向测试、严格 clippy、格式和 diff 检查通过。

## 数据与复现

环境为 macOS 26.6.2 arm64、Rust 1.94.0、release 构建；峰值内存通过
`/usr/bin/time -l` 测量。样本数量有限，固定查询集不能代表所有项目和搜索方式。

- [viberwhisper 历史原始记录](data/small-auto25-2026-09-09/viberwhisper-history.json)、[agentflow 历史原始记录](data/small-auto25-2026-09-09/agentflow-history.json)
- [源码、二进制身份及命令](data/small-auto25-2026-09-09/provenance.json)

[refresh_matrix.py](data/small-auto25-2026-09-09/refresh_matrix.py) 复用已有 16 项
小仓库查询，兼容二进制 manifest。执行参数见 provenance；输出必须指向未存在
的缓存目录。`analyze-frozen.py` 与 `analyze-history.py` 可重建各自汇总及 CSV。

[history_updates.rs](../history_updates.rs) 新增可重复的 `--query` 和独立的
`--update-query` 参数；未指定时保持原 vLLM 查询默认值。例如 viberwhisper：

```sh
cargo bench --bench history_updates -- \
  --root /absolute/path/to/viberwhisper \
  --variant main=/absolute/path/to/coderg-main \
  --variant auto50=/absolute/path/to/coderg-auto50 \
  --variant auto25=/absolute/path/to/coderg-auto25 \
  --end ab1f117d922fe06da6fc2f1f72605ba227ba4233 \
  --commits 100 --iterations 7 --warmup 3 \
  --query 'fn ' --query Transcription --query self --update-query 'fn ' \
  --workspace .cache/2026-09-09 --keep \
  --output .cache/2026-09-09/viberwhisper-history-rerun.json
```
