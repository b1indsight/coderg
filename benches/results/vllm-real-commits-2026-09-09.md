# vLLM 真实提交：双代更新与自动合并阈值

> 文档状态（2026-09-10）：历史阈值对照：下文 50% 源码及数字保留，最终大库阈值为 25%；B < 32 MiB 使用累计 8 MiB 重建。当前 release 结果见[三档实测](size-tiers-2026-09-10.md)。

> 后续默认值已改为 **`max(B × 25%, 8 MiB)`**，优先控制 M 的体积。
> 下文保留首次分析与 50% 源码归档，25% 的实测数据同样列在表中。

在 `feat/generational-index-refresh` 上逐个 checkout **500 个真实 first-parent
提交**，比较原来的双代手动维护版、M 达到 B 的 25%、M 达到 B 的 50% 三种方案。
本次初测当时采用 **`M >= max(B × 50%, 8 MiB)` 时自动合并 B 与 M**，移除 `compact --full`。
保留 `compact` 整理 M；大小阈值在内容刷新时检查，不按提交数触发。

500 次更新中，50% 方案触发 1 次基础段合并，总更新耗时 35.70 秒，手动维护版
为 35.34 秒；最终 M 从 44.14 MiB 降到 20.87 MiB。25% 方案触发 4 次，耗时
37.12 秒。三组固定查询的延迟接近，50% 是控制活动索引体积与维护次数的粗略
折中，不是经过精确调优的最优值。触发基础段合并的那次更新耗时 1.09 秒，属于
当前同步实现的明显尖峰。

## 数据与方法

- 日期：2026-09-09；macOS 26.6.2 arm64，Rust 1.94.0，release 构建。
- 仓库：[vllm-project/vllm](https://github.com/vllm-project/vllm)。本地原副本只有
  一个浅克隆提交；在独立缓存克隆中从上游加深 500 层，得到 501 个 first-parent
  提交。没有生成模拟 commit，也没有修改原 vLLM 工作区。
- 500 步范围：基线 `a5f82882a6afa08e65260704011de3321a3aa4a4`
  （2026-08-26）→ `569adb5a9780f9c02d22a6b29826acf711512356`（2026-09-06）。
  先对基线建索引，再依次 checkout 后续 500 个提交。
- 另先做最近 100 个真实提交的原版对照：基线
  `e55b93f2969d76b854eae158b6d17baea757d3e8`（2026-09-03）→ 同一终点。
  两轮起点不同，B、M 大小和耗时不能跨轮当成同一实验比较。
- 每个版本使用独立索引，共用当前 checkout 的源码；每步轮换版本执行顺序。
  更新计时是 checkout 后首次 `search -F -l SamplingParams` 的完整进程耗时，
  包含刷新、合并、查询和输出，不包含 Git checkout、额外验证或初始建索引。
  macOS 下用 `/usr/bin/time -l` 获取峰值 RSS。
- 每步状态只能更新一次，故每步更新测量 1 次；表中中位数/p95 是不同提交的
  延迟分布，p95 采用 nearest-rank。总耗时是这些更新的和，不是整套实验运行时间。
- 无变化查询在第 0、1、25、50、100、200、300、400、500 步采样，每组预热
  2 次、正式 5 次，交错版本；查询为 `AsyncMock`、`SamplingParams`、`class `，
  使用固定字符串和文件名输出模式，分别测默认刷新与 `--no-refresh`。
- 初次构建、每步更新及 4 次回退/前进后，三组查询均与
  `rg --hidden -g !.git -F -l` 对照完整文件集合和退出码。两轮共 **5,175 次对照
  全部通过**（100 步 630 次，500 步 4,545 次）。这不等同于完整正则功能验证。
- 字节大小均为逻辑文件长度，MiB = 1,048,576 字节。B/M 只计当前 manifest
  引用的 lookup/postings 文件，M 内可能还有过期 posting；不代表源码 diff 大小。

| 真实变更规模 | 最近 100 个提交 | 500 个提交 |
|---|---:|---:|
| 每步 Git 变化文件数，中位数 / p95 / 最大 | 2.5 / 21 / 94 | 2 / 17 / 194 |
| 变化文件计数之和（重复计数） | 598 | 2,522 |
| 新增 / 删除行数之和 | 42,844 / 3,589 | 137,131 / 21,628 |
| 目标版本变化文件完整字节，中位数 | 86,298 | 66,191 |
| 目标版本变化文件完整字节，总和 | 20,758,530 | 80,630,927 |

完整字节数不含已删除文件。coderg 按整文件重新索引，metadata、重命名及 ignore
处理可能使其刷新文件计数不同于 Git diff 的路径计数；原始记录同时保留两者。

## 先用 100 个真实提交验证原版差异

原版为主分支 `0ab2294a8097f52d7ea4a8a0167de6ea2697abdb` 的二进制。
双代手动维护版是本分支自动大小阈值加入前的版本。

| 100 步结果 | 原版 main | 双代手动维护 |
|---|---:|---:|
| 更新中位数 / p95，ms | 77.02 / 846.08 | 65.78 / 92.27 |
| 更新总耗时，秒 | 16.92 | 6.94 |
| 基础段重建次数 | 12 | 0 |
| 最终 B，MiB | 61.36 | 60.45 |
| 最终 M，MiB | 0.66 | 16.44 |

原版在第 8、16、…、96 步重新建 B；双代版移除了这个按段数触发的源码重建。
下面的阈值实验仅比较双代策略，基础段合并流式读取已有索引，不重新扫描全部
源码提取 gram。变化文件本身仍需读取并写入 M。

## 500 个真实提交：选择 50%

三组初始 B 都是 **58.69 MiB（61,542,456 字节）**，初始 M 为 0。

| 500 步结果 | 手动维护 | 自动 25% | 自动 50%（采用） |
|---|---:|---:|---:|
| 更新中位数，ms | 68.67 | 65.53 | 67.26 |
| 更新 p95，ms | 91.07 | 88.92 | 88.60 |
| 最慢更新，ms | 188.62 | 961.62 | 1,090.92 |
| 更新总耗时，秒 | 35.34 | 37.12 | 35.70 |
| 自动 B+M 合并次数 | 0 | 4 | 1 |
| M 内合并次数 | 299 | 242 | 269 |
| 更新完成后观测到的最大 M，MiB | 45.17 | 14.95 | 28.81 |
| 第 500 步 B，MiB | 58.69 | 61.36 | 60.17 |
| 第 500 步 M，MiB | 44.14 | 4.77 | 20.87 |
| 第 500 步总段数（B+M） | 8 | 8 | 9 |
| 更新过程最大 RSS，MiB | 49.28 | 105.41 | 112.09 |
| 第 500 步索引目录总量，MiB | 392.57 | 546.32 | 411.24 |

25% 在第 140、235、361、472 步触发，相关更新分别耗时
746、842、868、962 ms。50% 只在第 304 步触发：17 个文件变化，合并 10 个
B+M 输入段，共 92,368,480 字节，输出新 B 为 63,096,966 字节，M 清空。
这次合并输出约为输入的 68.3%，收益来自丢弃过期版本及重新编码；配置的 50%
是 **M/B 触发比例**，不是目标压缩率。

50% 的初始触发线是 29.35 MiB，合并后按新 B 调整为 **30.09 MiB**。之前
61.37 MiB 的 B 对应更新实验终点附近的源码快照；本轮从更早的真实提交开始，
因此初始 B 更小。B 都属于 vLLM，不是 Chromium。

| 提交步数 | 手动维护 M，MiB | 自动 25% M，MiB | 自动 50% M，MiB |
|---|---:|---:|---:|
| 100 | 9.31 | 9.31 | 9.31 |
| 200 | 20.88 | 11.13 | 20.88 |
| 300 | 28.75 | 11.24 | 28.75 |
| 304 | 29.39 | 10.79 | 0 |
| 400 | 33.50 | 3.40 | 9.14 |
| 500 | 44.14 | 4.77 | 20.87 |

M 不是单调增长：失效段引用会被移除，小合并会过滤旧版本。大小判断在本次
变化段写入并清理失效引用后执行；表中记录的是合并完成后的大小，不能当成
更新过程中绝不超过的上限。8 MiB 下限用于小仓库，本轮 vLLM 实验未触及它，
由规划器单元测试覆盖。

源码和命中文件集合也在变化，不能把差值全部归因于索引维护策略。

完成 500 步后继续在同一索引上执行四次真实历史切换，单位 ms：

| 切换 | Git 变化文件数 | 手动维护 | 自动 25% | 自动 50% |
|---|---:|---:|---:|---:|
| 500 → 499 | 4 | 60.71 | 66.93 | 66.05 |
| 499 → 250 | 870 | 206.70 | 219.59 | 225.92 |
| 250 → 0 | 997 | 213.72 | 969.24 | 236.58 |

## 实现与复现

- 自动大小判断在 [compaction.rs](../../src/compaction.rs)；无内容变化的搜索
  不做维护。每次内容更新最多一次合并，普通 M 小合并仍使用 8 段软上限、
  最多 4 个同量级输入、32 MiB 预算。基础段合并最多 32 个输入；旧索引更多
  输入时先缩减 M，后续内容更新再检查。
- 大合并同步持有写锁，因此会产生偶发较长更新，并让其他需要刷新的写者等待。
  已加载不可变快照的读取可继续。本次不是并发延迟压力测试。
- **尚无物理 GC**：活动 M 变小不等于目录磁盘占用下降。旧段保留给已有读者，
  因此自动合并还会增加待回收文件；表中单独列出了完整目录体积。
- 69 项 Rust 单元/集成测试通过，包含合并版本归属、删除/二进制过滤、并发
  刷新、大小阈值和被移除参数的拒绝；严格 clippy 与格式检查通过。
- 本轮只粗测 25%、50% 两个比例，没有扩大到 Chromium，也未精调阈值。

```sh
cargo bench --bench history_updates -- \
  --root /absolute/path/to/vllm-with-history \
  --variant manual=/absolute/path/to/coderg-manual \
  --variant auto25=/absolute/path/to/coderg-auto25 \
  --variant auto50=/absolute/path/to/coderg-auto50 \
  --end 569adb5a9780f9c02d22a6b29826acf711512356 \
  --commits 500 --iterations 5 --warmup 2 \
  --workspace .cache/2026-09-09 --keep \
  --output .cache/2026-09-09/real-history-rerun.json
python3 benches/results/data/vllm-real-commits-2026-09-09/analyze.py
```

`analyze.py` 汇总已归档的两份 JSON，重建 `summary.json` 和 `updates.csv`。
源码归档叠加在上述 main 提交上即为 50% 实测版；构建 25% 变体只修改
`FULL_COMPACT_PERCENT`。手动维护版源码保留在前一轮报告的数据归档中。
