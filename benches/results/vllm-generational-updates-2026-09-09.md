# vLLM 两代索引：100 次提交后的刷新与查询性能

> 文档状态（2026-09-10）：历史模拟提交试验。最终实现使用真实提交验证，小库改为累计 8 MiB 重建，大库采用 25% 合并；见[三档实测](size-tiers-2026-09-10.md)和[最终设计](../../docs/generational-index-refresh.md)。

> 后续已完成 [500 个真实 vLLM 提交测试](vllm-real-commits-2026-09-09.md)，
> 当时先采用 50%，随后改为 25%，并移除 `compact --full`。本文保留较早模拟实验的原始口径。

本轮在 `feat/generational-index-refresh` 上实现 B＋M 两代更新，并与主分支
`0ab2294a8097f52d7ea4a8a0167de6ea2697abdb` 的 release 二进制进行交错对照。
两种场景各有 100 个模拟 commit，每次修改 10 个文件、增加约 1000 行。

反复修改同一组文件时，100 次提交后首次搜索的总耗时从 **17.15 s 降到
6.22 s（−63.74%）**；分散修改 1000 个文件时，从 **19.17 s 降到
8.14 s（−57.51%）**。两种场景中旧版均重建基础段 12 次，新版均为 0 次。
新版的普通更新和小合并仍有成本，但避免了原版周期性的全量重建尖峰。

分散修改后的大范围回退更慢：例如从第 99 次提交回到第 50 次，490 个文件
变化，旧版通过 tree 缓存恢复耗时 84.88 ms，新版差异更新耗时 166.56 ms。
这符合取消历史 tree 快照的取舍；不能把正向更新的收益套用到所有回退场景。

## 方法

- 日期：2026-09-09；macOS arm64，Rust 1.94.0，release 构建；具体系统版本见 provenance。
- vLLM 基准提交：`569adb5a9780f9c02d22a6b29826acf711512356`。
  初始索引包含 6835 个文本文件、86,384,180 字节源码。
- 使用临时本地 Git 克隆；原 vLLM 工作区没有被修改。新旧索引位于源码目录外，
  共用同一份工作区内容，每步按奇偶交错执行，避免固定由同一版本先运行。
- 从 `vllm/` 下 1205 个大小在 8–128 KiB 的受版本控制 Python 文件中，按路径
  的固定散列顺序选择。`repeated` 始终修改相同 10 个文件；`rotating` 每次
  选择新的 10 个文件，100 步共修改 1000 个不同文件。
- 修改通过追加有效 Python 注释实现，每个文件每步增加 100 行，包括统一查询
  标记和步骤编号。因此这是受控的内容/索引维护实验，不能代表所有真实代码提交。
- 提交后的首次搜索执行 `search -F -l CODERG_COMMIT_BENCH`，包含文件快照
  检查、索引更新或合并、查询和输出。用 `/usr/bin/time -l` 收集 RSS，报告的
  wall time 包含该包装进程；不包含生成修改、Git commit 或独立正确性校验。
- 每个步骤只执行一次有状态的首次搜索；中位数/p95 描述这 100 个不同更新步骤
  的分布，p95 使用最近秩，不是同一个固定更新的重复测量置信区间。
- 查询检查点为 0、1、8、16、32、64、100 次提交，以及回到第 100 次状态并全合并
  之后。全合并仅对新版执行，旧版继续提供同内容状态的对照。分别测默认搜索和 `--no-refresh`，每项预热 3 次、交错计时 7 次。
  检查点不使用 time 包装，统计新 CLI 进程、热文件系统缓存的耗时。
- 每次构建、更新、回退及维护之后，对 `AsyncMock`、`SamplingParams` 和测试标记
  的完整匹配文件集合及退出码与 `rg` 比较。最终两组共 **1284 项对照全部通过**。

## 结果含义与边界

- repeated 的 M 旧段在下一次覆盖后失去有效文档归属，直接从活动引用中移除。
  因此新版始终只有 B＋一个 M 段，没有发生小合并；这部分收益来自版本引用整理。
- rotating 的新版执行了 44 次有预算的小合并，最多 9 个活动段，即 B＋8 个 M 段。
  第 100 步 M 为 24.38 MiB，活动索引为 86.93 MiB，高于旧版的 65.13 MiB。
  B 中被 M 覆盖的 posting 仍保留，这项空间代价到基础段合并时才会消除。
- 两个稳定查询在第 100 步的 no-refresh 中位数均值仍约 5.8–5.9 ms，默认搜索
  约 23–24 ms。本轮没有观察到随 100 次提交持续增长的明显查询延迟，但只测了
  这两个稳定关键词和一个增长标记，不代表整个正则查询矩阵。
- 回退统一比较当前 B＋M 的有效文件状态与目标工作区。大范围回退会读入变化文件
  的完整内容，因而放弃了旧版命中 tree 缓存的优势。这里每种状态转换仅测一次。
- 表中的普通 `compact` 在回退测试之后执行；此时 M 已被大范围更新收敛为一个
  段，所以它没有实际合并工作。`compact --full` 则确实重新生成了 B，分别耗时
  565.93 / 698.38 ms。这是单次样本，不能据此推断 Chromium 规模的合并时间。
- 两代实现仍使用完整 metadata 扫描，按长度和 mtime 检测变化，没有增加内容指纹。
  同长度同 mtime 的替换仍可能漏检；仅 mtime 变化也可能导致额外重新索引。
- 旧段尚未物理回收，磁盘占用仍会随更新累积。显式重型合并持有写锁，期间需要
  发布内容更新的搜索会等待；本轮性能数据没有测量这种并发等待。
- 初始构建仅各测一次：repeated 的 before/after 为 791.04/1301.31 ms，rotating
  为 822.83/839.00 ms。新增文件同步改变了写入路径，这些单次样本不足以判定
  构建性能回归；本轮主要结论限定为持续索引维护。

## 实现与验证

实现见 [两代更新说明](../../docs/generational-index-refresh.md)、
[刷新路径](../../src/index.rs)和[合并器](../../src/compaction.rs)。
manifest schema 和 lookup/postings v4 保持兼容；不再由段数或变化比例触发全量
重建，不再新增/恢复 tree 缓存。跨进程写锁保护修改，原子替换 manifest 发布结果。

全部 66 项 Rust 测试通过，严格 clippy、格式和 diff 检查通过。新增测试覆盖连续
更新和自动合并、合并后再次修改、删除/恢复/重命名/二进制转换、HEAD 变化与脏
工作区并存、六个并发刷新进程，以及源码暂时不存在时仍可完成显式全合并。
